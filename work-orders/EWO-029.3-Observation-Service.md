## 2. Purpose

Specify the engineering work required to implement the **Observation Service**: the cross-process, read-only service that exposes `ARCH-017`'s approved seven-operation observation catalogue over the Founder-approved Model B / `SPIKE-R3` local IPC transport, consuming `EWO-029.1`'s existing internal projection foundation without redesigning it.

## 3. Context

`EWO-029.1` built the Runtime-internal projection foundation (`runtime/src/observation.rs`) — pure, `pub(crate)`, transport-unaware functions computing all seven operations. `EWO-029.2` selected and empirically validated (Linux, macOS, Windows) the transport strategy: `interprocess` as the primary local IPC library, supplemented by direct `windows-sys` calls for Windows SID/impersonation handling, over Unix domain sockets (Linux/macOS) and Windows named pipes (Windows). Both are Founder-approved and complete. What remains unbuilt is the connective layer: an actual listening service that accepts local connections, authorizes the connecting principal, dispatches to `EWO-029.1`'s existing projection functions, and returns bounded responses — this work order.

## 4. Governing Sources

`ARCH-017` v0.2.2 §13–§32 (connection model, trust/authorization, discovery/endpoint, closed operation set, query/response contract, compatibility negotiation, reconnection, runtime safety, failure isolation/lifecycle independence, multiple clients, deployment/enablement); `EWO-029.1` v0.2.0 (the seven projection functions and their exact `ProjectionStatus` semantics, consumed unmodified); `EWO-029.2` v0.2.0 §9–§38 and its own §32/§33 Runtime/Observation-Service-Impact sections (the transport strategy and its implementation obligations); the `EWO-029.2` Independent Evidence Review's two carried-forward observations (`IER-TV-029.2-O01`/`O02`).

`ARCH-017` `document_id: ARCH-017` / `version: 0.2.2` / `status: Approved`. `EWO-029.1` `document_id: EWO-029.1` / `version: 0.2.0` / `status: Approved`. `EWO-029.2` `document_id: EWO-029.2` / `version: 0.2.0` / `status: Approved`. Model B and `SPIKE-R3` both Founder-approved. Linux/macOS/Windows platform validation: `SATISFIED WITH RECORDED NON-BLOCKING GAPS`. All thirteen `services/*` crates in `synapse-runtime` (`actor-directory`, `audit-pipeline`, `communication-provider`, `effect-coordinator`, `filesystem-provider`, `http-provider`, `persistence`, `process-provider`, `scheduler`, `sqlite-provider`, `supervisor`, `timer`, `timer-provider`) depend only on `synapse-common`/`synapse-api`, never on `runtime`; `runtime` depends on `services/audit-pipeline` (not the reverse) to reference the externally-defined `AuditPipeline` trait via `with_audit_pipeline` — the bootstrap-dependency shape this work order's own placement (§17) follows. All preconditions satisfied — no Engineering Stop triggered.

## 6. Engineering Problem

`EWO-029.1`'s own filed text states the gap directly: its projection module is "not yet part of this crate's own external public API... this module is the internal substrate a later, separately Founder-gated work order (`EWO-029.3`...) will extract, wrap, or redesign." `EWO-029.2` §33 states precisely what that later work order must do: "implement the chosen local-IPC accept loop; perform peer-credential-based authorization... before any query is served; implement the closed seven-operation dispatch over `EWO-029.1`'s existing projection functions; implement the bounded-work/rejection/abandoned-client-detection obligations; satisfy the first-instance pipe-creation and disciplined socket-path-placement obligations." This work order specifies exactly that gap-closing engineering.

## 7. Scope

In scope: an Observation Service component that (a) binds a local IPC listener via `interprocess` (Unix domain socket on Linux/macOS, named pipe on Windows), (b) authorizes each connecting peer via the empirically-validated same-user principal check (Unix `PeerCreds::euid()`; Windows impersonation → token → SID comparison, supplemented by direct `windows-sys`), (c) dispatches exactly the seven `ARCH-017` §17 operations directly to `EWO-029.1`'s existing `pub(crate)` projection functions — no visibility change (§17) — (d) maps each projection result to a bounded response, (e) enforces `ARCH-017` §28's bounded-work/rejection/abandoned-client-detection obligations, (f) implements the disciplined endpoint-placement and stale/graceful-cleanup behavior both platforms' validation runs already exercised, (g) implements the explicit Windows restrictive named-pipe security descriptor `IER-TV-029.2-O01` requires, (h) is wired into Runtime bootstrap strictly as the already-architected opt-in configuration point (`ARCH-017` §32) — never on by default.

## 8. Explicit Out-of-Scope

SDK public client API (`EWO-029.4`); connection/session/compatibility-negotiation protocol design (`EWO-029.5`); cross-platform conformance test suite as its own deliverable (`EWO-029.6`); GUI; Control Centre; remote access of any kind; a Runtime Control API (`D2`) or any mutation operation; actor creation/deletion; effect execution/retry/cancel commands; an eighth observation operation; an arbitrary diagnostics shell; authentication beyond the already-approved local-principal model; production installer/service-manager tooling; cloud deployment; mobile support; final wire-protocol/serialization format selection (§27–§28); SDK/CLI ergonomics.

## 9. Architecture Constraints

Direct application of `ARCH-017` throughout, no reinterpretation: §9 Authority Model (projections only, never a second authority); §10 SDK-mediation rule (out of scope here, binds `EWO-029.4`); §13 Connection Model (connect → trust check → compatibility negotiation → session → operations, in that fixed order); §16 Sessions (exists-or-doesn't, no per-operation granularity); §28/§29 (bounded work, non-starvation, client-failure isolation, Observation-Service-lifecycle independence from Runtime bootstrap); §30 (must not structurally foreclose multiple clients); §32 (opt-in-at-bootstrap, absent by default).

## 10. Transport Constraints

Founder-approved, not reopened: `interprocess` primary library; direct `windows-sys` for Windows SID/impersonation; Unix domain sockets (Linux/macOS), Windows named pipes (Windows); synchronous-first (no async runtime introduced); local-only (no TCP, no HTTP, no WebSocket, no remote form of any kind — `interprocess` local-socket/named-pipe APIs only, exactly as both validation harnesses already used).

## 11. Security Constraints

Every accepted connection must pass the platform-appropriate same-user principal check *before* any operation from the closed set is reachable (`ARCH-017` §13 step 2, fail-closed). Linux/macOS: `interprocess::local_socket::traits::StreamCommon::peer_creds().euid()` compared against the service's own `libc::getuid()` — the exact mechanism both validation harnesses already proved. Windows: `impersonate_client()` → `OpenThreadToken`/`GetTokenInformation`/`ConvertSidToStringSidW` → compare against the service's own `OpenProcessToken`-derived SID — the exact chain the Windows validation harness already proved end-to-end. PID is never used as, or substituted for, principal identity anywhere. Mismatch → `Unauthorized`, disclosing nothing beyond that outcome (`ARCH-017` §14).

## 12. Runtime Authority Boundary

The Observation Service acquires **no** authority over actor lifecycle, capabilities, effects, supervision, persistence, or diagnostics — every field it returns traces to one of `EWO-029.1`'s existing, unmodified projection functions, which themselves already enforce this (`&Runtime`-only, no `&mut Runtime` anywhere). This work order adds a consuming layer on top; it does not touch `EWO-029.1`'s own logic.

## 13. Observation Operation Catalogue

Exactly the seven operations `ARCH-017` §17 defines:

| # | Operation | Input | `EWO-029.1` Projection Function |
|---|---|---|---|
| 1 | `GetRuntimeStatus` | none | `runtime_status(&Runtime)` |
| 2 | `ListDurableActors` | none | `durable_actors(&Runtime)` |
| 3 | `GetActorDetail` | known/enumerated `ActorId` | `actor_detail(&Runtime, &ActorId)` |
| 4 | `ListCapabilities` | known `ActorId` | `capabilities(&Runtime, &ActorId)` |
| 5 | `ListEffects` | known `ActorId` (or effect id) | `effects(&Runtime, &ActorId)` |
| 6 | `GetSupervisionRelationship` | known `ActorId` | `supervision(&Runtime, &ActorId)` |
| 7 | `GetDiagnostics` | none, or known `ActorId` | `diagnostics(&Runtime, Option<&ActorId>)` |

No eighth operation. No generic dispatch by string method name — the dispatch surface this work order builds must itself remain a fixed match over exactly these seven, mirroring `EWO-029.1`'s own closed-set discipline.

## 14. Service Responsibilities

Own: listener bind/accept lifecycle; peer authorization; the fixed seven-way dispatch; projection-to-response mapping; bounded concurrency/rejection; endpoint create/cleanup. Do not own: any Runtime-authoritative state (owned exclusively by the components `ARCH-007`/`008`/`011`/`012`/`016` and `EWO-029.1`'s own projection functions already establish); any client-facing wire schema beyond what §27–§28 gate.

## 15. Lifecycle

Direct application of `ARCH-017` §29, restated as concrete engineering obligations, not aspirational prose: (1) Observation Service bind/initialization failure must not fail Runtime bootstrap; (2) Runtime must operate correctly, indefinitely, with the service never configured or having since failed; (3) service failure/restart must never require a Runtime restart; (4) existing sessions terminate on service unavailability as an ordinary `Unavailable` transition, not a Runtime-level failure; (5) Runtime-owned actor/lifecycle/effect/capability/persistence/supervision semantics remain entirely unaffected by service state, in every case. Concretely: the service runs on dedicated thread(s), never sharing the Runtime's own execution path (`ARCH-017` §28's own explicit permission), and its own failure is caught and contained at that boundary, never propagated into Runtime's own control flow. These are runtime-behavior properties, not crate-boundary properties: a panic on a dedicated thread does not, by default, crash the process or other threads, and this containment is achievable identically under this work order's in-crate placement (§17).

## 16. Platform Behavior

Linux/macOS: Unix domain socket, bound inside a dedicated, restricted-permission runtime directory (§22); peer credentials via `interprocess::PeerCreds`. Windows: named pipe, `\\.\pipe\...`-local form only, created with exclusive first-instance semantics (`interprocess`'s own default-on `FILE_FLAG_FIRST_PIPE_INSTANCE` behavior, empirically confirmed working by `EWO-029.2`'s own validation run) plus an explicit restrictive security descriptor (§18). Cross-platform semantic differences (differing syscalls, differing credential-field availability, differing cleanup models) are never hidden behind a false uniform abstraction — `EWO-029.2` §20/§37's own disclosed lesson is inherited unmodified here.

## 17. Transport Integration / Production Placement

The Observation Service is implemented **inside the `runtime` crate itself**, as a module alongside `EWO-029.1`'s existing `runtime/src/observation.rs` — no new crate is introduced. This placement mirrors `EWO-029.1`'s own established precedent for the identical underlying question (the projection foundation itself was placed as a Runtime-internal module rather than a new crate, for the same reasoning applied here). `EWO-029.1`'s seven projection functions remain `pub(crate)` — no visibility promotion is required, since the Observation Service's dispatch code shares the same crate and can call them directly.

`interprocess` and target-gated `windows-sys` are declared as direct dependencies of the `runtime` crate itself (§30). This is a disclosed, deliberate cost: every consumer of `runtime`, including any that never enable observation, gains these two crates in their own compile graph (`windows-sys` remains properly target-gated and is not compiled on non-Windows targets; `interprocess` is not target-gated and is present unconditionally at compile time, even though the code path using it is never executed unless observation is explicitly configured at bootstrap, per `ARCH-017` §32). Whether this cost is further bounded via an optional Cargo feature flag is an implementation-time packaging decision (§35), not fixed by this work order.

This placement keeps the Observation Service entirely within the established `runtime → services/*` dependency direction this workspace already uses everywhere else (e.g. `runtime` depends on `services/audit-pipeline` to reference the externally-defined `AuditPipeline` trait via `with_audit_pipeline`; no `services/*` crate depends back on `runtime` anywhere in this workspace). No new crate, and therefore no dependency-direction exception, is introduced by this work order.

**Alternative considered and not selected.** A trait-based inversion — defining the Observation Service's transport-facing interface in `synapse-common`/`synapse-api` (which both `runtime` and a new `services/observation` crate would depend on), with `runtime` implementing that trait internally and a separate `services/observation` crate owning the transport/listener/dispatch code — was evaluated as a structurally sound alternative that would keep `interprocess`/`windows-sys` isolated to a single, non-core crate. It was not selected: it requires inventing where the seven request/response shapes and a new dispatch trait live, a design surface this work order's own §8 places out of scope; it offers no isolation benefit that the in-crate placement's own thread-level failure containment (§15, §23) does not already provide; and the Observation Service has no pluggability requirement anywhere in `ARCH-017` that would justify the added structural complexity, unlike genuinely swappable backends such as `services/scheduler` or `services/persistence`.

## 18. Windows ACL Obligation (mandatory — carries `IER-TV-029.2-O01` forward)

`EWO-029.2`'s own validation run explicitly established only default-path security-descriptor *feasibility*, never exercise of an actual restrictive descriptor. This work order **requires**, as a mandatory acceptance criterion (§27, item 11): construction of an explicit named-pipe security descriptor restricting access to exactly the same-OS-user-or-explicitly-configured-additionally-trusted-user set `ARCH-017` §14 already defines; explicit analysis of what the descriptor does *not* accidentally grant (no broad `Everyone`/`Authenticated Users`/`Users` group grant); explicit inheritance-flag consideration; a real runtime test proving an unauthorized principal is refused *at the pipe-security-descriptor layer*, not merely at the impersonation/SID-comparison application layer already validated. Exact Win32 descriptor-construction code is not written by this work order — the acceptance criterion, not the implementation, is specified here.

## 19. Unix Endpoint Security

Carried forward from `EWO-029.2`'s own already-empirically-confirmed findings, as mandatory implementation requirements: bind inside a dedicated, restricted-permission (verified `0700`-class) runtime directory — directory permission, not socket-file mode, is the real enforcement boundary (`EWO-029.2`'s own `MV-07` finding); explicit pre-bind path-type verification before any unlink, never a blind `remove_file` on an arbitrary pre-existing path (symlink/TOCTOU caution); explicit stale-vs-graceful distinction (`interprocess`'s own default-on `reclaim_name` already self-cleans graceful shutdown, empirically confirmed on both Linux and macOS — genuine abnormal termination remains the real gap requiring explicit handling).

## 20. macOS Path-Length Requirement

`EWO-029.2`'s validation empirically confirmed macOS's `sockaddr_un.sun_path` capacity (104 bytes) is smaller than Linux's (108 bytes) — a real platform constraint, not a universal application constant. This work order requires the chosen runtime-directory path scheme to remain comfortably within the smaller (macOS) limit on every platform, not merely within Linux's more permissive one.

## 21. Stale Endpoint Handling

See §19 — restated as its own acceptance criterion (§27, item 14): safe behavior for abnormal termination that never blindly deletes an unrelated filesystem object, verifies expected path type first, and does not assume graceful-shutdown cleanup (§19's `reclaim_name` behavior) covers the genuine-crash case, which it does not.

## 22. Projection Semantics

Consumed unmodified from `EWO-029.1`. In particular, explicitly preserved, not regressed: `GetActorDetail`'s corrected `Complete`/`None` vs. `Complete`/`Some` semantics (no live instance is a *definitive* answer, never `Unavailable`); `ListCapabilities`' full, truthful `Complete` projection including the declared retry constraint; `ListEffects`' no-silent-drop, truthful-`Partial`-on-correlation-gap behavior and its `ROI-16` payload exclusion (no field beyond identity/status/provider ever crosses this boundary); `GetDiagnostics`' honest `Unsupported` result under current evidence. This work order's own dispatch/mapping layer must not reinterpret, narrow, or "improve" any of these — it is a thin transport-facing wrapper, not a second implementation.

## 23. Failure Isolation

Direct restatement of `ARCH-017` §28/§29 as engineering obligations: bounded observation work; bounded concurrent in-flight work per connection; bounded response size; rejection/failure once bounds are exceeded; detection and forced disconnection of an abandoned/unresponsive client, never indefinite resource holding on its behalf. A crashed, hung, disconnected, or malformed-request-sending client must never affect Runtime availability, correctness, or performance beyond these explicit bounds.

## 24. Connection Model

Minimum required, not over-designed: one accepted connection at a time per thread/worker, synchronous request → response → (repeat until disconnect) → close; no multiplexing, no subscription, no long-lived event feed, no streaming — none of which `ARCH-017` §18/`ROI-06` requires or permits for Phase 1. Concurrency strategy (thread-per-connection vs. a small bounded worker pool) is an Open Decision (§35), not finalized here, since `ARCH-017` §30 requires only that the design *not structurally foreclose* multiple simultaneous clients, not that a specific concurrency model be mandated.

## 25. Compatibility Boundary

`ARCH-017` §19's own compatibility-negotiation model (tier/version-range exchange at session establishment) is real but its exact wire encoding remains explicitly deferred (`ROC-15`) — this work order implements the negotiation *point* in the connection sequence (§9's own fixed ordering) without finalizing its wire representation, which belongs to whichever of §27/§28's own gated decisions eventually resolves it, informed by whatever `EWO-029.5` itself later requires. No compatibility work is pulled forward beyond establishing that the sequencing slot exists. Phases through internal dispatch/response mapping (§36, Phase 4) may use Rust-level, explicitly non-normative internal test representations of requests/responses; this does not select or pre-empt `EWO-029.5`'s own eventual wire-format decision.

## 26. Diagnostics / Runtime Status / Actor Detail / Effects / Capability / Supervision Boundaries

`GetDiagnostics` remains observation-only — no remote shell, no arbitrary command execution, no log or config mutation, matching `EWO-029.1`'s own already-honest `Unsupported` result exactly. `GetRuntimeStatus` reports Runtime state without the service itself becoming a second owner of that state. `GetActorDetail`'s corrected semantics are preserved (§22). `ListEffects`' `ROI-16` payload boundary is preserved (§22). `ListCapabilities` remains strictly informational, no grant/revoke/change authority. `GetSupervisionRelationship` remains strictly informational, no supervisory control operation of any kind.

## 27. Acceptance Criteria

1. Service starts without changing Runtime authority.
2. Local endpoint binds on Linux, macOS, and Windows.
3. An authorized same-user client is accepted.
4. A mismatched-principal client is rejected, fail-closed, before any operation is reachable.
5. Exactly the seven §13 operations are exposed.
6. All seven operations remain read-only (no test, static or dynamic, finds a mutation path).
7. Runtime remains authoritative and fully operational throughout every test scenario, including service failure.
8. Observation Service crash does not crash Runtime.
9. Client crash/hang does not crash or stall Runtime.
10. `Complete`/`Partial`/`Unavailable`/`Unsupported` statuses are preserved unmodified from `EWO-029.1`.
11. Windows named-pipe restrictive security descriptor is implemented and its refusal behavior is verified at runtime (§18).
12. Windows SID same-user verification works (already empirically proven at the library/harness level by `EWO-029.2`; re-proven here at the service's own integration level).
13. Unix endpoint directory security (restricted permissions, path-type-checked cleanup) is verified.
14. Stale endpoint (genuine abnormal termination) is handled safely, distinct from graceful-shutdown self-cleanup.
15. No remote transport exists anywhere in the implementation.
16. No production mutation API exists anywhere in the implementation.
17. No new Runtime authority is introduced.
18. No GUI dependency exists anywhere in the implementation.
19. The Observation Service module compiles and links within the `runtime` crate with no dependency-graph cycle (§17, §41).

## 28. Test Strategy

**Unit:** dispatch mapping (exactly seven, no eighth); principal-comparison logic, including the negative/mismatch case — satisfied via deterministic synthetic-data unit tests (comparing two known-different principal values), *not* requiring a live second OS account; `ProjectionStatus` pass-through mapping. **Component:** Observation Service exercised in-process against a real `Runtime` instance (mirroring `EWO-029.1`'s own existing test pattern). **Cross-process:** local client ↔ service, on Linux, macOS, and Windows, covering accept/authorize/dispatch/respond/disconnect. **Security:** mismatch rejection (both platforms); Windows restrictive-descriptor refusal test (§18); Unix directory/endpoint permission verification; stale-vs-graceful endpoint behavior. **Regression:** no eighth operation; no mutation authority; no transport fallback to TCP/HTTP/WebSocket of any kind; dependency graph remains acyclic (§17).

## 29. Cross-Platform Verification / CI Requirements

The published `EWO-029.2` macOS/Windows validation infrastructure (`.github/workflows/ewo029-2-transport-validation.yml`) already demonstrated concrete value — real bugs were found and fixed specifically *because* real platform execution was exercised, not merely type-checked. This work order **requires** permanent cross-platform CI (Linux, macOS, Windows) for the Observation Service's own test suite, following that same established, cost-aware pattern — the exact workflow/CI file changes themselves are not authored here, only the requirement. `IER-TV-029.2-O02` (the `actions/checkout` Node.js deprecation warning) is carried forward as CI maintenance follow-up only — not a service-architecture requirement.

## 30. Dependency Policy

Direct `interprocess` use is declared directly in `runtime`'s own `Cargo.toml`, under `[dependencies]`. Direct `windows-sys` use is declared directly under `runtime`'s own `[target.'cfg(windows)'.dependencies]` section — never relied upon transitively through `interprocess`, preserving the dependency-hygiene rule both `EWO-029.2` validation harnesses already demonstrated in practice. Whether these are declared as mandatory or `optional = true` dependencies gated behind a Cargo feature is an implementation-time decision (§17, §35), not fixed here. No async runtime dependency is introduced (§10).

## 31. Error Semantics

High-level categories only, as needed for engineering clarity, not final wire-level codes (deferred, §25): unauthorized principal; malformed/unsupported request; operation unsupported; projection unavailable; projection partial; transport failure; compatibility failure; timeout; internal service failure. This maps directly onto all eight of `ARCH-017` §27's own error-taxonomy categories — no competing taxonomy is introduced.

## 32. Resource Bounds

Bounded concurrent clients; bounded request size; bounded response buffering; hung-client detection and forced disconnection; no resource leak across the connect/disconnect cycle. This is local developer-platform infrastructure, not a production-scale multi-tenant server — do not over-engineer beyond `ARCH-017` §28's own stated bounds.

## 33. Connection Concurrency

Open Decision (§35): thread-per-connection (simplest, directly matches both validation harnesses' own already-proven pattern) vs. a small bounded worker pool. `ARCH-017` §30 requires only non-foreclosure of multiple simultaneous clients, not a specific model.

## 34. Risks

| Risk | Mitigation Direction |
|---|---|
| Principal-validation regression during transport-layer integration | Component-level tests re-exercise the exact same-user/mismatch logic already proven at the harness level (§28) |
| Windows ACL misconfiguration (wrong SID, wrong access mask, unintended inheritance) | Explicit §18 acceptance criterion with a real runtime refusal test, not merely a "hook reachable" check |
| Stale Unix endpoint cleanup race | Explicit path-type verification before any unlink (§19/§21), never a blind delete |
| Accidental mutation/control leakage through the dispatch layer | Fixed seven-way match, no generic dispatch, regression-tested (§28) |
| Operation-set drift (an eighth operation creeping in) | Regression test asserting exactly seven; any addition requires an `ARCH-017` amendment first, per that document's own §17 rule |
| Service/Runtime lifecycle coupling creeping in during integration | §15's explicit acceptance criteria (7, 8, 9) directly test against this |
| Platform-specific behavior divergence being silently papered over | §16's explicit no-false-uniformity discipline, inherited from `EWO-029.2` |
| Protocol/serialization decision leaking into this work order prematurely | §25/§27–§28's explicit deferral boundary |
| `interprocess`/`windows-sys` version drift | `EWO-029.2`'s own version-currency-check precedent should be repeated at implementation time |
| Dependency-direction / Cargo-cycle regression (a future `services/*` crate accidentally depending on `runtime`, or the reverse) | Dependency graph verified (`cargo tree` / manual `Cargo.toml` inspection) before implementation begins and again before commit/filing; the in-crate placement (§17) eliminates this specific risk structurally, by construction, since the Observation Service is not a separate crate |

## 35. Open Decisions

Observation Service placement is settled at §17: in-crate within `runtime`, no new crate. The constraint sections above (§9–§32) each state their own hard boundary inline; this section consolidates them into explicit, checkable Stop conditions.

**STOP-01 — Dependency Cycle.** If the Observation Service's own placement introduces, or would require, a Cargo dependency cycle of any kind — STOP. Do not resolve by silently redesigning the placement; return to Independent Review.

**STOP-02 — Unsupported Public Runtime API Exposure.** If implementation requires promoting `EWO-029.1`'s seven projection functions, or any other Runtime-internal machinery, to broader public visibility beyond a narrowly justified interface (§17) — STOP.

**STOP-03 — `EWO-029.3`/`EWO-029.5` Inseparability.** If implementation cannot proceed through dispatch/response mapping (§36, Phase 4) without prematurely deciding `EWO-029.5`-owned session/wire/compatibility semantics (§25) — STOP.

**STOP-04 — Runtime Authority Transfer.** If Observation Service implementation requires ownership or mutation of any Runtime-authoritative state (§12) — STOP.

**STOP-05 — Operation Set Expansion.** If an eighth operation, or any generic mutation/control endpoint, becomes necessary (§13) — STOP; any addition requires an `ARCH-017` amendment first.

**STOP-06 — Security Boundary Failure.** If local-principal authorization (§11) cannot be enforced fail-closed on a supported platform — STOP.

**STOP-07 — Windows ACL Failure.** If a safe, restrictive Windows named-pipe security descriptor cannot be implemented and empirically verified (§18) — STOP.

**STOP-08 — Architecture Conflict.** If implementation requires amendment to `ARCH-017` or any other governing architecture document — STOP, and return to the architecture lifecycle, not this work order's own authority.
