## 2. Purpose

To define the formal, cross-platform conformance stage the Observation foundation's own governing architecture already requires (`EWO-029.5` §33) but has not yet had authored: real-execution proof, on Linux, Windows, and macOS, that the completed Observation Service (`EWO-029.3`), wire protocol (`EWO-029.5`, `synapse-observation-wire`), and Foundation Observation Client (`EWO-029.4`) behave conformantly together — and, separately, closes `EWO-029.3` §29's own pre-existing, still-unfulfilled requirement for permanent cross-platform CI covering that same stack.

## 3. Context

`EWO-029.1` through `EWO-029.5` are each Approved; `EWO-029.5` has received Final Founder Implementation Acceptance (2026-08-12, `1474c921e841e3cbcc9da947aff737c46d177f7a`, carrying `IIR-029.5-F01`/`F02`/`O01`/`O02` forward as acknowledged non-blocking items). The complete stack is implemented, unit-tested, and end-to-end tested on Linux (this engagement's own development environment); real-executed on Windows (Founder-run `EWO-029.3 Observation Service Windows Production Validation` Run #6 and `EWO-029.3 Observation Service Windows ACL Cross-Principal Validation` Run #3, both `SUCCESS` on `main` at `360cb2b`); and has **no execution evidence of any kind on macOS** — the only macOS CI in the repository (`ewo029-2-transport-validation.yml`) validates raw `interprocess` transport primitives from the `EWO-029.2` evaluation stage, predating the Observation Service, wire protocol, and SDK client entirely, and does not exercise any of them.

Separately, `EWO-029.3` §28 itself already states, as a requirement of that already-Approved work order: "Cross-process: local client ↔ service, on Linux, macOS, and Windows, covering accept/authorize/dispatch/respond/disconnect," and `EWO-029.3` §29 separately states: "This work order **requires** permanent cross-platform CI (Linux, macOS, Windows) for the Observation Service's own test suite... the exact workflow/CI file changes themselves are not authored here, only the requirement." No such permanent CI currently exists for Linux or macOS; only two Windows workflows exist, both `workflow_dispatch`-only (manual, not automatically triggered on every change).

## 6. Engineering Problem

The Observation Service/wire/SDK stack is fully implemented and Founder-accepted, but its cross-platform correctness is asymmetrically evidenced: comprehensively real-tested on Linux and Windows, entirely untested on macOS, and covered nowhere by *permanent* (automatically re-run) CI on any platform. What is the narrowest formal conformance stage that closes this gap — proving equivalent behavior on all three target platforms and establishing the permanent CI `EWO-029.3` §29 already requires — without redesigning, re-architecting, or extending the already-accepted implementation?

## 7. Scope

In scope: real-execution conformance testing of the existing Observation Service, `synapse-observation-wire`, and Foundation Observation Client on Linux, Windows, and macOS; establishing permanent (CI-triggered, not `workflow_dispatch`-only) coverage for Linux and macOS; formally incorporating the two already-executed, Founder-run Windows workflows as this work order's own Windows evidence; a conformance requirement matrix and objective acceptance criteria against `ARCH-017`/`EWO-029.3`/`EWO-029.5`'s own already-approved behavior.

## 8. Explicit Out-of-Scope

New Observation operations; new wire-protocol generations; new SDK capabilities; new Runtime mutation APIs; remote networking or remote Observation Service access; telemetry, metrics, or tracing; query/history APIs; Control Centre or GUI functionality of any kind; production refactoring for test convenience alone; any new security model or policy not already required by `ARCH-017`/`EWO-029.3`/`EWO-029.5`; redesign of the wire protocol, session model, or authorization model; `EWO-028`'s own unblocking.

## 9. Architecture Constraints (not reopened)

Seven-operation closed set; six wire error categories; JSON Lines framing; `max_request_bytes`/`max_response_bytes` semantics; two-phase compatibility parse; connection-is-session model; Windows no-parse-before-authorization ordering; Unix/macOS peer-credential-before-read ordering; local-only endpoint policy — all `EWO-029.3`/`.4`/`.5`-established, all Founder-Accepted, none revisited here. This work order tests conformance to these; it does not restate, relax, or extend them.

## 11. Linux Requirements

A permanent GitHub Actions job (`runs-on: ubuntu-latest` or equivalent) running, unmodified: `cargo test -p synapse-observation-wire --locked`, `cargo test -p synapse-runtime --lib --locked`, `cargo test -p synapse-sdk --locked`, `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`. No new Linux-specific test content is anticipated — existing coverage (including the real cross-process `unix.rs` end-to-end test and the `sdk/tests/observation.rs` real Runtime↔SDK end-to-end tests) already exercises the full stack; this item is CI-infrastructure only.

## 12. Windows Requirements

No new Windows test content. Three distinct things must not be conflated:

1. **Evidence already obtained**, entirely independent of this work order's own existence: `EWO-029.3 Observation Service Windows Production Validation` (Run #6, `main`, `360cb2b`, `SUCCESS`) and `EWO-029.3 Observation Service Windows ACL Cross-Principal Validation` (Run #3, `main`, `360cb2b`, `SUCCESS`), both Founder-run in satisfaction of `EWO-029.5` §34's own already-mandatory Windows production regression requirement — obtained before `EWO-029.6` was drafted, not produced by it.
2. **Evidence incorporated by this work order**: this Draft formally records and adopts that pre-existing evidence as its own Windows conformance evidence (§10, this section), per Founder direction (§6 of the governing authoring task) — an act of recognition, not of re-execution.
3. **Work this work order itself still performs for Windows**: none beyond that recognition. No new Windows test content, no new Windows workflow, no restructuring of the existing two workflows — their separation (regression-guard-first, security-validation-second) reflects a deliberate, already-justified design (`.github/workflows/ewo029-3-observation-service-windows-acl-cross-principal-validation.yml`'s own header comment) this work order has no basis to disturb (§16, Production-Code/Infrastructure Boundary).

## 13. macOS Requirements

Real execution, on a genuine `macos-latest` (or equivalent) GitHub Actions runner, of the identical Linux test commands (§11) — `synapse-observation-wire`, `synapse-runtime --lib` (including the real cross-process `unix.rs` end-to-end test, which is `#[cfg(unix)]`, not `#[cfg(target_os = "linux")]`, and therefore already covers macOS at the source level without modification), and `synapse-sdk` (including the real Runtime↔SDK end-to-end tests). Cross-compilation is explicitly insufficient (Founder direction, item 2) — a real `macos-latest` run is required, and not merely because both platforms happen to be Unix-family: the `interprocess` crate's own peer-credential implementation (the mechanism `unix.rs`'s same-user authorization check depends on) uses genuinely different underlying OS facilities per platform — Linux's `SO_PEERCRED`/`ucred` versus the BSD-derived `xucred` struct (with its own `cr_version` compatibility check) macOS, FreeBSD, and related platforms use instead. A passing Linux run says nothing, by construction, about whether `peer_creds().euid()` resolves correctly through that structurally different macOS code path — this is precisely why real macOS execution, not cross-compilation and not "it's Unix, it'll work" inference, is required. `EWO-029.3` §20's documented macOS-specific constraint (`sockaddr_un.sun_path` capacity: 104 bytes on macOS vs. 108 on Linux) must similarly be confirmed non-violated by the existing endpoint-path construction under real macOS execution, not merely asserted from the Linux-authored comment. No macOS-specific *production* code is anticipated; if the existing `#[cfg(unix)]` implementation and tests do not run unchanged on macOS, that is itself a finding for this work order's own Independent Review, not license to add macOS-specific production code without a separate Founder decision (§19 Production-Code Boundary; STOP-029.6-01, §22).

## 14. Permanent CI Requirements

Closes `EWO-029.3` §29's own requirement, which states this work order "requires permanent cross-platform CI (Linux, macOS, Windows)... **following that same established, cost-aware pattern**" — an explicit reference to the already-existing `EWO-029.2` transport-validation workflow (`ewo029-2-transport-validation.yml`), which is itself `workflow_dispatch`-only. Independently confirmed: **every workflow currently in this repository** (`ewo029-2-transport-validation.yml`, `ewo029-3-observation-service-windows-validation.yml`, `ewo029-3-observation-service-windows-acl-cross-principal-validation.yml`) is `workflow_dispatch`-only; no automatically-triggered (`push`/`pull_request`) workflow exists anywhere in this repository's history. This evidence materially supports reading "permanent" as *persistent, reproducible, repository-owned validation infrastructure ready to be run* — the sense in which `EWO-029.2`'s own workflow is already "permanent" despite being manual-only — rather than necessarily requiring automatic triggering.

Founder Architecture Approval (2026-08-12, §26 Question A) resolved this evidence into an explicit ruling: "permanent CI" does not require automatic `push`/`pull_request` triggering. Persistent, repository-owned, reproducibly executable `workflow_dispatch` infrastructure satisfies this work order's own requirement, provided it remains checked into the repository, can be reproducibly executed on the required target platform, the conformance suite it runs is objectively defined, and successful execution evidence is recorded before Founder Implementation Acceptance. Automatic triggers remain a future implementation/operational option, not a normative requirement of this document. Implementation may therefore use a `workflow_dispatch`-only matrix of `ubuntu-latest`/`macos-latest`/`windows-latest`, matching 100% of existing repository precedent, or a `push`/`pull_request`-triggered matrix, at the implementation team's own discretion (§26 Question C), provided the required permanent evidence exists for Linux, macOS, and Windows. Whichever is chosen, the same shared test commands (§11) apply, reusing rather than duplicating existing test content. Windows's own two specialized security-validation workflows (§12) remain separate regardless of which structure is chosen — they require Windows-specific orchestration (ephemeral local-account creation, impersonation) a shared matrix job does not need and should not attempt to generalize, and must remain intact per Founder Decision C.

## 15. Security Conformance Requirements

Windows: already discharged (§12) — same-user success, cross-principal denial via a genuine second local Windows account/SID, `ERROR_ACCESS_DENIED` (5), post-denial server health, no-parse-before-authorization ordering, all real-executed and Founder-confirmed. Unix/macOS: the existing peer-credential (`PeerCreds::euid()`) same-user check, already covered by real execution on Linux and (per §13) to be covered by real execution on macOS. Whether a genuine cross-principal (different-user) refusal test is *also* required on Unix/macOS was genuinely ambiguous in governing text: `EWO-029.3` §28's "Unit" test category explicitly states principal-mismatch coverage does not require a live second OS account, but that same section's separately-listed "Security" category states "mismatch rejection (both platforms)" without repeating that carve-out. Founder Architecture Approval (2026-08-12, §26 Question B) resolved this: this work order SHALL NOT introduce a new mandatory Windows-style live second-principal/second-user validation harness for Linux or macOS unless implementation evidence shows that such a test is required to prove an existing Approved security guarantee. Linux and macOS MUST still validate the applicable platform-local security boundary and peer-principal behavior already required by existing architecture — the existing peer-credential (`PeerCreds::euid()`) same-user check, real-executed on Linux and (per §13) to be real-executed on macOS. No new security model is authorized, no new cross-principal requirement is invented, and no OS-user orchestration harness is required merely for symmetry with Windows. If implementation reveals that an existing Approved mismatch-rejection guarantee cannot be objectively proven without genuine second-principal execution, that is an Engineering Stop (STOP-029.6-04, §22), returned to the Founder — not resolved unilaterally under this work order's own authority.

## 16. Protocol Conformance Requirements

For each platform (§10): endpoint creation; endpoint connection; first-request `WireVersionProbe`/generation-1 establishment; established-generation persistence across repeated requests on one connection (no renegotiation); all seven operations (`GetRuntimeStatus`, `ListDurableActors`, `GetActorDetail`, `ListCapabilities`, `ListEffects` both `EffectSelector` forms, `GetSupervisionRelationship`, `GetDiagnostics`); malformed-request handling; `max_request_bytes` enforcement; `max_response_bytes` enforcement and the detail/detail-free/close-without-response fallback chain; `Partial` reserved for genuine Runtime-observed partiality only, never fabricated for wire-capacity loss; disconnect behavior (clean EOF, mid-session drop); local-only endpoint behavior (no host:port form reachable). Evidence for each item MAY come from existing tests where the same code path already covers the target platform (e.g., `#[cfg(unix)]` code exercised identically by real execution on both Linux and macOS) — this work order does not require a platform-triplicated, mechanically identical test suite.

## 17. SDK Conformance Requirements

`ObservationClient::connect`, all seven `ObservationSource` methods, wire-DTO-to-semantic-view mapping, and the wire-error-category-to-`ObservationClientError` mapping (`UnsupportedQuery`/`UnavailableInformation`/`RuntimeSideFailure`/`CompatibilityFailure`/`MalformedRequest`/`Timeout`, plus the client-local `ConnectionFailure`/`AuthorizationFailure` synthesis rules) — real-executed on all three platforms per §10.

## 18. Reuse of Existing Evidence

This work order authorizes no new production code and, wherever existing tests already provide the required evidence for a given platform, authorizes no new test code either — only its real execution in a permanent CI context it does not currently have. Existing assets this work order builds on, unmodified: `synapse-observation-wire`'s own 51 unit tests; `runtime/src/observation_service.rs`'s and `unix.rs`'s own unit and real cross-process tests; `sdk/tests/observation.rs`'s real Runtime↔SDK end-to-end tests; `runtime/tests/observation_service_windows_validation.rs`; `.github/validation/ewo029-3-acl-cross-principal/`; the two existing Windows workflows.

## 19. Production-Code Boundary

**This work order begins with the expectation that no production code changes are required.** If implementation reveals that genuine cross-platform conformance cannot be achieved without changing `runtime/`, `sdk/`, or `observation-wire/` production behavior, that is **not** authorized by this document — it is an Engineering Stop (§22), returned to the Founder for a separate architecture/scope decision, never resolved unilaterally under this work order's own authority. A conformance work order that quietly becomes a feature-development work order is exactly the failure mode this boundary exists to prevent.

## 20. Test Design Principle: Equivalent Evidence, Not Mechanical Symmetry

Platforms differ in what a genuinely meaningful test looks like (Windows requires impersonation/SID comparison and a real second local account for its cross-principal proof; Unix/macOS use peer credentials and have no equivalent live-second-account requirement established anywhere in governing architecture). This work order requires **equivalent architectural evidence** for each conformance item per platform (§16, §17), not an artificially identical test mechanism reproduced three times. Where a single, already-existing test (e.g., `#[cfg(unix)]` code) genuinely covers two platforms by construction, real-executing it once per platform is sufficient; no platform-specific reimplementation is required merely for symmetry's own sake.

## 21. Acceptance Criteria

**Linux:** real execution of §11's commands — PASS. Permanent, repository-owned `workflow_dispatch` (or, at implementation discretion, automatically-triggered) CI per §14/Founder Decision A — PASS.
**Windows:** existing real execution (§12, Runs #6/#3) — PASS (already satisfied; evidence obtained *before* this work order existed and formally incorporated by it, per §12's own distinction between evidence obtained, evidence incorporated, and work this document itself still performs). Required security validation (§15) — PASS (already satisfied). Permanent CI for Windows's own two specialized security-validation workflows — remaining `workflow_dispatch`-only and structurally separate, per §14/Founder Decisions A and C.
**macOS:** real execution of §11's commands on a genuine `macos-latest` runner — PASS required, not yet satisfied. Permanent CI — PASS required, not yet satisfied.
**Shared protocol/service/SDK conformance** (§16, §17), evidenced per platform per §20 — PASS on all three platforms.
**No architecture regression** — confirmed via `cargo test --workspace --locked` and `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` remaining clean on every platform.
**No production behavior added** unless a separate Founder authorization is obtained after an Engineering Stop (§19, §22).
**No weakening or skipping of a failing test to achieve a green CI result** — a failing platform-specific test is a finding, never silently disabled, `#[ignore]`d, or loosened to pass.

## 22. Engineering Stops

**STOP-029.6-01** — Production behavior change required to achieve conformance on any platform.
**STOP-029.6-02** — Public API change (Runtime, SDK, or wire crate) required.

**STOP-029.6-06** — Existing, already-Approved behavior genuinely cannot pass on one target platform (as opposed to merely lacking a CI job to prove it).
**STOP-029.6-07** — Platform behavior would require semantic divergence (not mere implementation adaptation) between platforms.

## 26. Founder Decisions

Resolved by Founder Architecture Approval, Denver Jacobs, Founder, 2026-08-12 (§29, Disposition):

- **Question A — CI trigger semantics. RESOLVED.** "Permanent CI" does not require automatic `push`/`pull_request` triggering. Persistent, repository-owned, reproducibly executable `workflow_dispatch` infrastructure satisfies this work order's own requirement, provided: it remains checked into the repository; it can be reproducibly executed on the required target platform; the conformance suite it runs is objectively defined; and successful execution evidence is recorded before Founder Implementation Acceptance. Automatic triggers remain a future implementation/operational option, not a normative requirement of this document.
