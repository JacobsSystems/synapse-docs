## 1. Purpose

Determine, through explicit evidence and comparative evaluation, which transport technology or transport architectural model should be recommended for `ARCH-017`'s approved Runtime Observation / Connectivity boundary — resolving the concrete answer to every "Technology Question"/"remains a Technology Question" `ARCH-017` itself repeatedly and deliberately left open (§13, §14, §15, §18, §19, §33, §44 of that document).

## 2. Scope / Non-Goals

In scope: transport requirement extraction from `ARCH-017`; candidate discovery, research, and evaluation; a mandatory-requirements gate; a weighted comparative decision matrix; a reasoned recommendation, explicitly separated from Founder approval. Out of scope, and none of the following is performed by this document: transport implementation; Runtime modification; Observation Service creation; SDK connectivity code; `EWO-029.3` authoring; GUI/Control Centre engineering.

## 3. Governing Sources Read

`ARCH-017` v0.2.2 (full text, §1–§50, read directly, not from memory); `ARCH-015` v0.2.0 §10 (`DPB-INV-01` Runtime Authority); `ARCH-016` v0.2.1 §13–§15 (connection model, observation/synchronization, staleness); `ARCH-014` v0.8.0 (cited by `ARCH-017` for SDK tier vocabulary, not independently re-read in full — no transport-relevant content there); `ARCH-008` §29 (Future Compatibility table — Windows/Linux/macOS Control Centre and "cross-platform Runtime hosts... no platform-specific mechanism" precedent); `GOV-018` v0.2.0 §5 (Enduring Principle 7: "A minimal, capability-secure core, extended only through ordinary, auditable mechanisms" — the direct constitutional basis for `ARCH-017` §32's opt-in-by-default decision, and the lens this evaluation applies to attack-surface scoring).

Independently reconfirmed engineering-context fact, not architecture-mandated but materially relevant: `synapse-runtime`'s workspace `Cargo.toml` declares **zero external (non-workspace-path) dependencies anywhere**, and no crate in the workspace uses `async`/`.await` or any async runtime. Whatever this evaluation recommends will be the first external dependency and, if it requires an async runtime, the first async-runtime adoption in this codebase's history — a materially larger commitment than "pick a library," disclosed and weighted explicitly below (§8, `RTR-11`).

During its Narrow Technology Evaluation Correction stage, this evaluation additionally incorporated the governing Independent Technology Evaluation Review itself as a source, along with the further external research that review performed: Windows named-pipe instance-squatting mitigation (`FILE_FLAG_FIRST_PIPE_INSTANCE`-class exclusive-creation semantics), Unix domain socket path-placement best practice (dedicated, restricted-permission runtime directories vs. world-writable shared directories), Linux abstract-namespace Unix-socket availability, and `tonic`'s own Windows named-pipe transport support (found to require a hand-built custom connector, with no built-in support existing).

`RTR-04`, `RTR-05`, `RTR-06`, and `RTR-10` are, on inspection, predominantly **implementation-structure** requirements (how the Observation Service is built) rather than properties any of the candidate transports themselves preclude or guarantee — every candidate below can be implemented to satisfy them (e.g., via a dedicated OS thread never sharing the Runtime's own execution path, per `ARCH-017` §28's own explicit "satisfiable by dedicated threads/executors... none is mandated here"). ## 5. Candidate Discovery Method

Candidates were drawn from the seed list of realistic local-IPC technology families, cross-checked against current Rust-ecosystem evidence, and organized first by **architectural model** (§6), since Unix domain sockets and Windows named pipes are not competing technologies but complementary halves of one possible model — collapsing them into two separate candidate rows would produce a straw-man comparison.

## 6. Candidate Longlist

1. **Model A — one identical transport technology across all OSes**, realized as: (1a) loopback TCP (raw), (1b) HTTP over loopback, (1c) HTTP/2 / gRPC over loopback or UDS, (1d) WebSocket over loopback, (1e) QUIC.
2. **Model B — one SynapseOS transport abstraction backed by platform-native local transports** (Unix domain sockets on Linux/macOS, Windows Named Pipes on Windows), realized as: (2a) hand-rolled via minimal per-platform bindings, (2b) via the `interprocess` crate's existing cross-platform `local_socket` abstraction.
3. Platform-native IPC families considered and excluded from further evaluation without full comparison: D-Bus (Linux/systemd-oriented, not first-class on Windows/macOS — fails `RTR-03` outright); shared-memory/ring-buffer IPC (e.g., `iceoryx2`) — wrong paradigm, built for high-frequency pub/sub data-plane traffic, not a synchronous, session-oriented, authorization-gated request/response control plane; Windows COM/WinRT — Windows-only, fails `RTR-03`.

## 7. Candidate Shortlist

Model A: loopback TCP (raw, application-framed), gRPC/tonic (HTTP/2), WebSocket, QUIC.
Model B: platform-native IPC (Unix domain sockets + Windows named pipes) via either a hand-rolled minimal binding or the `interprocess` crate.

## 8. Excluded Candidates (with reasons)

- **D-Bus** — excluded before full evaluation: fails `RTR-03` (no first-class Windows/macOS story; it is a Linux desktop-session convention, not a general cross-platform local-IPC mechanism).
- **Shared-memory ring buffers (e.g., `iceoryx2`)** — excluded: wrong paradigm for a session-oriented, authorization-gated, closed seven-operation query/response boundary; these technologies solve a different problem (maximal-throughput pub/sub telemetry between trusted, already-co-located processes with no per-message authorization model).
- **Plain HTTP/1.1 or HTTP/2 without gRPC** — excluded from independent full evaluation: offers nothing over raw loopback TCP or UDS at seven fixed operations except an HTTP parsing/framing layer with no compensating benefit; folded into the loopback-TCP and gRPC analyses instead of a standalone row.

## 9. Platform-Native IPC Model Evaluation (Model B)

**`RTR-01` (local connectivity):** Native — both Unix domain sockets and Windows named pipes exist for exactly this purpose.

**`RTR-02` (peer identity) — the decisive dimension.** Unix domain sockets: peer credentials are retrieved via `SO_PEERCRED`/`getsockopt` on Linux, and `getpeereid` on macOS/BSD — both deliver the actual OS UID (and GID) of the connecting process, kernel-enforced, unspoofable by the client. **Classification: Native.** Rust std's own `UCred` equivalent is currently gated behind the nightly-only `peer_credentials_unix_socket` feature — meaning stable Rust needs `libc`/`nix` or a wrapping crate to reach it, not std alone. Windows named pipes: identity is established via `ImpersonateNamedPipeClient` + `GetTokenInformation` (or `GetNamedPipeClientProcessId`/`...SessionId` for the coarser process/session identity), which is Windows' own native security-principal (SID) mechanism, kernel/security-subsystem enforced. **Classification: Native, via OS integration.** Both platforms deliver a real OS-security-principal identity *to the listening end without any supplementary application-layer mechanism* — exactly what `ARCH-017` §14 requires as the strong case ("not satisfied by a transport that cannot deliver any peer-identity signal... without such a supplementary mechanism").

**`RTR-03` (cross-platform):** Both halves are first-class, mature, OS-native primitives on their respective platforms — this is precisely what makes them *not* naturally "one identical technology." Windows named pipe semantics (ACL-based, session/token-oriented) and Unix-socket semantics (filesystem-path-based, credential-oriented) are **not identical** — disclosed explicitly, not glossed over, in the Cross-Platform Risk Register (§20).

**`RTR-09` (local-only-by-default):** Structurally the strongest candidate class: neither Unix domain sockets nor Windows named pipes are network-reachable *at all* — there is no IP stack, no port, nothing to accidentally bind to `0.0.0.0`. Local-only is not a configuration choice here; it is a structural property of the primitive itself. Both platform-native halves carry their own named, disclosed endpoint-integrity obligation, distinct from this structural strength — Unix domain sockets require disciplined socket-path placement (§12, §36), and Windows named pipes require disciplined first-instance/exclusive-creation semantics (§13, §36). Neither obligation changes Model B's standing relative to the alternatives (§36 shows every candidate carries comparable or worse endpoint-integrity exposure), but "no network port" must not be read as "no attack surface at all" — it is the smallest attack surface among the serious candidates, not a zero one.

**`RTR-11` (dependency/async footprint):** std has no built-in named-pipe support at all — Windows named pipes require either raw FFI (`windows-sys`, Microsoft's own minimal, declaration-only bindings crate — deliberately smaller and faster to compile than the legacy `winapi` crate) or a wrapping crate. Peer credentials on Unix require `libc`/`nix` regardless, since std's own equivalent is nightly-only. **Either way, at least one new external dependency is unavoidable for Model B** — but it can remain a small, single-purpose, non-async one (`libc` + `windows-sys`) if hand-rolled, or one focused, actively-maintained, non-tokio-mandatory crate (`interprocess` — 12.4M all-time downloads, ~424k/month, 23 published versions, tokio support explicitly feature-gated **off by default**) if not. Neither path forces adoption of an async runtime.

**Verdict: `RTR-01`–`03`, `09`–`10` native/strong; `RTR-02` is the strongest of any candidate researched.**

## 10. Single-Transport Cross-Platform Model Evaluation (Model A generally)

Common properties across every Model-A variant below: none has a native, kernel-delivered OS-peer-identity mechanism the way a local socket does — TCP, HTTP, gRPC, WebSocket, and QUIC all identify a *network connection*, not an *OS process/user*. Every Model-A variant therefore requires a **supplementary application-layer authorization mechanism** (e.g., a random token written to a file readable only by the intended OS user, presented on connect) to satisfy `RTR-02` at all — `ARCH-017` §14 explicitly permits this ("or an equivalent supplementary authorization mechanism MUST be separately justified"), so this does not eliminate any Model-A candidate outright, but it is a real, disclosed, structural cost every one of them shares and Model B does not.

## 11. Loopback TCP Evaluation

**`RTR-01`/`03`:** Universal — every target OS has a TCP/IP stack. **`RTR-02`:** Weak/Application-layer mechanism required (§10). **`RTR-09`:** The single largest structural risk of any candidate: a loopback-bound listener is one misconfigured bind address (`0.0.0.0` instead of `127.0.0.1`, or a misunderstood dual-stack/IPv6 default) away from becoming LAN-reachable — a class of mistake structurally impossible with Unix sockets/named pipes. Port allocation is also a genuine, disclosed operational question (fixed port risks collision with another local service; ephemeral port requires the discovery mechanism `ARCH-017` §15 already defers as a Technology Question, adding coupling between two open questions). **`RTR-11`:** Zero new dependency if hand-rolled directly on `std::net::TcpListener` — no crate needed at all, a genuine advantage. **Ecosystem/tooling:** unmatched — universally debuggable with any TCP tool. **Overall:** eligible at the mandatory gate only if paired with a real application-layer credential mechanism and disciplined bind-address handling; scores materially lower than Model B on security and structural-safety grounds, highest on tooling/simplicity-of-dependency grounds.

## 12. Unix Domain Socket Evaluation

Linux: `SO_PEERCRED`. macOS/BSD: `getpeereid`/`LOCAL_PEERCRED` — **not identical syscalls**, a genuine cross-platform nuance (§20). Filesystem-path-based; cleanup of a stale socket file on abnormal termination is a real, disclosed operational concern (a stale path can cause `EADDRINUSE`-equivalent failure on restart) — mitigated at implementation time by binding to a fresh, process-scoped path or removing a stale, verified-dead socket before bind, not designed here. Permissions are enforceable both via filesystem mode bits on the socket path *and* via peer-credential verification at accept time — belt-and-suspenders, stronger than either alone.

**Security dimension of path placement.** Socket-path *placement* is a security-relevant decision, not merely an operational cleanup concern: a predictable path in a world-writable directory (e.g. `/tmp`) is subject to real, named symlink/TOCTOU/endpoint-substitution attack classes (e.g. the "Nimbuspwn"-style vulnerability pattern). Mitigation direction, not designed here: place the socket inside a dedicated runtime directory with appropriately restricted ownership and permissions rather than a broadly world-writable shared directory; an `XDG`-runtime-directory-class location is an example of the desired property, not a hard-coded path. This is distinct from, not a replacement for, the stale-path *liveness* concern above — one is a security/endpoint-integrity issue, the other is a cleanup issue, and the two must remain independently tracked (§36).

**Linux abstract namespace, non-binding implementation note.** Linux additionally supports an **abstract-namespace** Unix-socket variant (no filesystem path at all, sidestepping stale-path and symlink/TOCTOU risk entirely by construction) — confirmed Linux-specific, unavailable on macOS/BSD/Windows. This is disclosed here as a possible future Linux-specific hardening option for `EWO-029.3`'s own eventual implementation to knowingly accept or decline; it is **not** adopted as the cross-platform Unix baseline, and does not alter this evaluation's own filesystem-path-based assumption, which remains portable and correct for comparison purposes. macOS remains, and must remain, based on filesystem-backed Unix-domain-socket assumptions, restricted-directory placement, and its own distinct `getpeereid` peer-identity mechanism — the abstract-namespace option is never promoted to the macOS or cross-platform baseline.

## 13. Windows Named Pipe Evaluation

ACL/security-descriptor-based access control at pipe-creation time, plus per-connection identity via impersonation/token inspection — **two independent enforcement layers**, matching Unix sockets' own belt-and-suspenders structure. Async Rust support exists today specifically via `tokio::net::windows::named_pipe` (Tokio's own documented module) — meaning the *async* path for named pipes is more discoverable in the ecosystem today than a *sync* one; a sync/blocking implementation is still fully possible via direct Win32 FFI (`windows-sys`) but has less ready-made example code, a genuine, disclosed operational-complexity cost if the sync-first direction (§9, `RTR-11`) is chosen. Operational complexity: named pipes require no filesystem cleanup (the pipe namespace is not the filesystem, and pipes are automatically reclaimed by the OS when the last handle closes) — simpler lifecycle than Unix sockets in this one specific respect.

**Named-pipe squatting / instance-creation race.** Windows named pipes are subject to a well-documented, actively-studied attack class in which an attacker-controlled local process pre-creates a pipe of the expected well-known name before the legitimate Observation Service does, potentially causing a connecting client to reach the attacker's pipe instead, or preventing the legitimate service from claiming the name at all. This is classified as a form of local endpoint spoofing/instance-creation race, bounded by `ARCH-017` §14's own same-OS-user threat model exactly as every other disclosed risk in this evaluation is — it does not claim protection against an already-compromised same-user process, only against a different, unauthorized OS user or an unprivileged squatting attempt the same-user boundary is meant to exclude.

**Mitigation direction (implementation-level, not designed here):** exclusive/first-instance pipe-creation semantics — e.g., Windows' own `FILE_FLAG_FIRST_PIPE_INSTANCE`, which fails pipe creation with `ERROR_ACCESS_DENIED` if an instance already exists, whose exact behavior must be verified during `EWO-029.3` implementation, not assumed here — layered together with the already-established restrictive ACL-at-creation and per-connection peer-principal verification, and `ARCH-017`'s own general fail-closed discipline (§14).

**Local-only discipline:** the Model B recommendation is, and must remain, **strictly local named-pipe connectivity** (`\\.\pipe\...`-class local pipes) — Windows named pipes also support a remote-server addressing form in the wider platform, which this evaluation does not recommend, evaluate, or authorize; `EWO-029.3` must not accidentally introduce remote named-pipe exposure, which would silently reopen `ARCH-017` §33/§36's local-only scope.

## 14. HTTP Evaluation

Not independently scored (§8) — strictly dominated by either loopback TCP (if no HTTP semantics are needed, which they are not: `ARCH-017` §17 already defines a fixed, closed operation catalogue, not a URL-routed resource model) or by Model B with a simple length-prefixed framing (if identity matters more than HTTP tooling, which `ARCH-017` §14 says it does).

## 15. HTTP/2 Evaluation

Not independently scored — HTTP/2's own advantages (multiplexed streams, header compression) address a distributed, many-concurrent-request, network-latency-bound problem this local, seven-operation, same-machine boundary does not have. Considered only as gRPC's transport (§16).

## 16. gRPC Evaluation

**`RTR-01`/`03`:** Strong — `tonic` supports both loopback TCP and Unix domain sockets as its own transport (`tonic::transport::server::UdsConnectInfo`), giving it a path to inherit UDS's own peer-identity properties on Unix. **`tonic` has no built-in Windows named-pipe transport.** Achieving Windows named-pipe connectivity through `tonic` would require a hand-built custom connector wrapping `tokio::net::windows::named_pipe` in `AsyncRead`/`AsyncWrite` — the same integration pattern the community `tonic-ws-transport` project uses for WebSocket transport. This does not make gRPC technically infeasible on Windows — it remains a viable, comparatively weaker candidate — but it means gRPC does not eliminate the platform-specific Windows integration work Model B already requires; it adds that same work on top of `tonic`/`prost`/`hyper`/`h2`/`tower`/`tokio`'s full dependency tree, for no corresponding `RTR-02` advantage over Model B. **`RTR-02`:** the credential surface `tonic` exposes at the application layer is oriented toward TLS peer *certificates* (mTLS), not OS peer *credentials* — confirmed via `tonic::Request`'s own documented `peer_certs()`. Reaching actual OS UID/GID through a `tonic`-over-UDS server would require dropping to the same lower-level socket APIs Model B already uses directly. **`RTR-11`:** by far the heaviest dependency tree of any candidate. **Strengths, genuinely earned:** first-class multi-language client generation and a large, mature ecosystem. **Overall: eligible, deferred, not rejected** — its genuine strengths remain correctly credited in the scoring (§24), just correctly outweighed at the stated, sensitivity-tested weights (§24a); its real strength (language interop) is explicitly not yet a governing requirement.

## 17. WebSocket Evaluation

Solves a persistent, bidirectional, push-capable connection problem. `ARCH-017` §18/`ROI-06` requires only synchronous request/response for Phase 1, and §37 explicitly defers push/subscription as a *future, separately architected* extension. No concrete, present advantage identified. **Deferred**, explicitly tied to §37's own future trigger, not rejected outright.

## 18. QUIC Evaluation

Mandatory TLS 1.3 (protocol-level, cannot be disabled) — introduces a full certificate/PKI identity model where `ARCH-017` §14 already specifies a *different*, OS-native identity model; no OS-peer-credential concept exists in QUIC at all. QUIC's own actual strengths (multiplexing over lossy/high-latency networks, connection migration) address problems that do not exist on a same-machine loopback path. Heaviest cryptographic dependency surface of any candidate (`quinn` + `rustls`/`aws-lc-rs`). **Rejected** — disproportionate complexity for the actual, local-only, same-user problem.

## 19. Other Candidates Considered

None beyond §6's longlist met the discovery bar for full evaluation; the exclusions in §8 are the complete disposition of every remaining candidate identified during research.

## 20. Cross-Platform Risk Register

The central lesson: "cross-platform" for Model B means **equivalent guarantee via different mechanism**, not **identical mechanism**, for peer credentials, permissions, endpoint naming, and cleanup; async behavior is not directly relevant since this recommendation is synchronous-first on both platforms. Specific divergences: `SO_PEERCRED` (Linux) vs. `getpeereid` (macOS/BSD) — different syscalls, different struct shapes; ACL-plus-impersonation (Windows) vs. credential-at-accept (Unix) — structurally different mechanisms achieving an equivalent guarantee, not equivalent mechanisms; Linux's own abstract-namespace option (§12) is not available on macOS/BSD/Windows and must not become the assumed baseline.

## 25. Primary Recommendation

**Transport architecture recommendation: Model B — a SynapseOS-owned local IPC abstraction backed by platform-native transports**: Unix domain sockets on Linux/macOS, Windows Named Pipes on Windows; fully synchronous (blocking, thread-per-connection or a small fixed worker pool), matching this workspace's own existing zero-async house style rather than introducing an async runtime; never loopback-network-based. Baseline lead over the runner-up: **1.10 points** (§24).

**Library-level recommendation: not resolved by this evaluation.** Two realistic options, both consistent with the architecture recommendation above:

- **(a) Hand-rolled**, via `libc` (Unix, peer-credential syscalls) and `windows-sys` (Windows, minimal official Microsoft FFI bindings) directly — narrowest possible dependency surface, most consistent with the workspace's zero-external-dependency precedent, highest implementation/maintenance burden on SynapseOS itself.
- **(b) The `interprocess` crate** — a single, actively-maintained, synchronous-by-default (tokio support is an opt-in feature, off by default) cross-platform local-socket abstraction already solving exactly this Model-B problem, at the cost of one moderately-sized third-party dependency sitting between SynapseOS and the OS.

## 26. Runner-Up

**Loopback TCP, paired with an explicit application-layer credential mechanism** (e.g., a per-process random token written to a file readable only by the launching OS user, presented on connect) — the strongest Model-A candidate, chosen as runner-up specifically for its zero-new-dependency path (if hand-rolled on `std::net` alone) and unmatched cross-platform tooling uniformity, at the accepted cost of a structurally weaker, bolt-on identity/attack-surface posture that Model B does not need to bolt on at all. Preserved as runner-up for traceability and possible future reconsideration, not weakened by Model B's subsequent Founder approval.

## 27. Rejected/Deferred Candidates

D-Bus and shared-memory IPC — rejected, architectural (mandatory-gate failure). QUIC — rejected, comparative (passes the gate technically, decisively dominated on fit). gRPC/tonic and WebSocket — explicitly **deferred**, not rejected, each tied to a concrete, named future trigger (§21).

## 28. Recommendation Confidence

- **Transport architecture/model confidence: MEDIUM-HIGH.** Model B is strongly evidenced and, per §24a, robust across every reasonable reweighting tested — not inflated to High, since the developer-platform-heavy scenario shows a materially narrower margin than the baseline alone would suggest.
- **Exact library/implementation confidence: LOW-MEDIUM.** Genuinely unresolved by documentation research alone; resolving it responsibly requires the empirical evidence a proof-of-concept would produce (§30).

## 29. Unresolved Questions

1. Hand-rolled vs. `interprocess` crate — which actually costs less engineering effort and produces more reliable peer-identity results across all three OSes in practice?
2. Empirically confirmed peer-credential retrieval on macOS (`getpeereid`) — documented, not exercised.
3. Empirically confirmed Windows named-pipe client-identity retrieval against `ARCH-017` §14's actual requirement — documented, not exercised.
4. Concrete latency/throughput characteristics of a synchronous, thread-per-connection Model-B implementation under `ARCH-017` §28's boundedness requirement.
5. `tonic`'s Windows named-pipe transport maturity — **Resolved** (§16): no built-in support exists; a custom connector would be required, reinforcing rather than weakening the case for Model B.

## 30. Proof-of-Concept (Technology Spike) Requirement

- **Before Founder Transport Architecture Approval (of Model B as the model): Spike useful but not blocking.** The model-level evidence (§9–§24a) is sufficiently robust and sensitivity-tested to support a Founder decision on the architecture itself without first requiring empirical proof.
- **Before `EWO-029.3` implementation or exact library commitment: Spike required.** Unresolved Questions 1–4 (§29) remain genuinely open and must be resolved empirically before committing to hand-rolled bindings, the `interprocess` crate, or any other specific implementation path.

**Founder Model-vs-Library Approval Boundary:** the Founder may approve **Model B as the transport architecture** without yet approving `interprocess`, direct OS APIs, Tokio-based transport implementation, `windows-sys`, any serialization, any wire framing, or any Observation Service implementation — every one of those remains a separate, later, `EWO-029.3`-or-later decision this document does not make.

**Spike scope, not performed by this document:** a minimal, throwaway program on each of Linux, macOS, and Windows that (a) accepts one local connection via the platform-native mechanism, (b) retrieves and prints the connecting peer's OS identity, (c) does so using both the hand-rolled and `interprocess`-crate paths for direct comparison, (d) determines whether a common SynapseOS abstraction can normalize the required semantics without weakening either platform's security guarantee, and (e) is deleted or archived outside the production workspace once its questions are answered — not implemented as part of this evaluation, and not implemented without separate Founder authorization.

## 36. Security Risk Register

| Risk | Candidate(s) | Severity | Mitigation Direction | Residual Concern |
|---|---|---|---|---|
| Unauthorized local client (different OS user) | All | High if unmitigated | Mandatory peer-credential check before any session (`ARCH-017` §14) | None beyond the disclosed same-user threat boundary |
| Accidental external/LAN exposure | Model A (TCP-based) only | Medium-High | Loopback-only bind, verified at implementation/test time | Structurally impossible for Model B |
| **Windows named-pipe squatting / instance-creation race** | Model B (Windows half) | Medium | Exclusive/first-instance creation semantics (e.g. `FILE_FLAG_FIRST_PIPE_INSTANCE`, exact behavior verified at implementation), restrictive ACL at creation, per-connection peer-principal verification, strictly local (never remote-addressed) pipe usage | Disclosed, implementation-level; bounded by the same-user threat model, not eliminated by it |
| **Unix domain socket unsafe path placement (symlink/TOCTOU/endpoint substitution)** | Model B (Unix half) | Medium | Place the socket in a dedicated, restricted-ownership/permission runtime directory (an `XDG`-runtime-directory-class location is an example of the desired property), never a broadly world-writable shared directory; exact path selection deferred to `EWO-029.3` | Disclosed, implementation-level; does not affect Linux/macOS peer-credential verification itself, which remains an independent, layered control |
| Stale Unix socket path after abnormal termination | Model B (Unix) | Low | Verified-dead-socket cleanup before bind (distinct from the placement risk above — this is a liveness/cleanup concern, not a spoofing one) | Disclosed, implementation-level |
| Malformed request | All | Low-Medium | Bounded parsing, per `ARCH-017` §28/§29 | Implementation-level |
| Resource exhaustion / slow-client starvation | All | Medium | Bounded concurrency, timeouts, forced disconnection (§28/§29) | Implementation-level, transport-agnostic |
| Transport library vulnerability (CVE in a dependency) | gRPC (large tree) > `interprocess` > loopback-raw/hand-rolled | Model-dependent | Prefer smallest dependency surface satisfying requirements | Directly favors Model B / hand-rolled or minimal-crate paths |
| Platform semantic differences causing an authorization inconsistency | Model B | Medium | Explicit per-OS test coverage in the spike and later implementation | Disclosed, §12/§13/§20 |
| Authentication bypass via a misconfigured additional-trust allow-list | All | Medium | `ARCH-017` §14's own fail-closed default | Architecture-level mitigation, transport-agnostic |
| Cleanup failure (leaked socket/pipe handle) | Model B | Low | OS-level automatic reclamation (pipes) / implementation-level cleanup (sockets) | Low residual |

## 37. Cross-Platform Risk Register

Covered in full at §20; the central lesson is that "cross-platform" for Model B means equivalent guarantee via different mechanism, not identical mechanism, for peer credentials, permissions, endpoint naming, and cleanup; async behavior is not directly relevant since this recommendation is synchronous-first on both platforms.

## 38. Technology Lock-In Analysis

Model B, properly abstracted behind one SynapseOS-owned trait/module boundary (whether backed by hand-rolled bindings or the `interprocess` crate), couples only the Observation Service's own accept/authorize loop to the chosen library — Runtime, SDK, and Control Centre all remain decoupled from that choice, consuming only the resulting typed session/query interface (§34/§35). This is a clean abstraction boundary specifically because `EWO-029.1`'s projection functions already take `&Runtime` and know nothing about transport (confirmed, direct source inspection). Serialization/wire-framing is not selected by this document and is not coupled to the transport choice — a small, explicit length-prefixed framing plus a workspace-consistent encoding (itself a future, separate decision) is sufficient at seven fixed operations and does not require adopting a general-purpose serialization framework.
