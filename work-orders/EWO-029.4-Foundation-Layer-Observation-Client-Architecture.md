## 2. Purpose

Define the **Foundation-layer SDK Observation Client**: the synchronous, typed, unmediated `synapse-sdk` API through which a separate consumer process invokes `ARCH-017`'s seven closed operations (already implemented and empirically validated by `EWO-029.3`) and receives typed, freshness-annotated projections — concretizing `ARCH-017` §31's own resolution of `ROC-18` ("Foundation Layer, Experimental API tier") into an actual engineerable surface, the identical relationship `EWO-029.3` already established between itself and `ARCH-017` §9/§13–§32 for the service side.

## 3. Context

`EWO-029.3` built and empirically validated (Linux, Windows, including genuine cross-principal ACL refusal) the Observation Service — the listening, authorizing, dispatching service side of `ARCH-017`'s connectivity architecture. Nothing on the client side exists yet: no SDK type, no client-facing method, no error taxonomy realization. `ARCH-017` §31 already classified where this client surface belongs (Foundation Layer, Experimental tier) and what it must and must not do; `ARCH-014` §5/§8/§10–§13 already define the SDK's own four-layer structure and tiering discipline this client must fit into. `EWO-029.1`, `EWO-029.2`, and `EWO-029.3` each independently, consistently named this work order "the SDK Foundation-layer Observation Client," distinct from `EWO-029.5`'s own "connection/session/compatibility-wire-format" scope — this work order closes exactly that gap, and no other.

## 9. Architecture Constraints (not reopened)

Model B — preserved, not reopened. `SPIKE-R3` — preserved, not reopened. Observation Service placement (Runtime-hosted, in-crate) — preserved, not reopened; this work order introduces no `services/observation → runtime` or equivalent dependency inversion. Runtime authority — the Observation Client owns no Runtime domain state, mutates none, and acquires no lifecycle, capability, supervision, or effect authority; serialization/protocol code introduced downstream by `EWO-029.5` must not become a second authority boundary either. Read-only boundary — preserved absolutely; no view type or method anywhere in this architecture carries mutation capability. Seven-operation closed set — `ARCH-017` §17's exact seven operations, closed, extensible only by future architecture amendment, never by unilateral implementation. Public Runtime API — not broadened by this work order in any way. Existing Unix/Windows local-principal security architecture (`EWO-029.3`, empirically validated, `STOP-07` cleared) — preserved unweakened throughout.

## 10. Foundation-Layer Placement

**Decision:** `sdk::foundation::observation` — a submodule of the existing Foundation layer, realized by restructuring `foundation.rs` into `foundation/mod.rs` (retaining its own existing, unchanged pure-re-export content and doc-comment invariant) plus a new `foundation/observation.rs` — **not** a fifth top-level sibling module alongside `ergonomics`/`extension`/`foundation`/`prelude`.

Rationale: `synapse-sdk`'s existing structure has an exact 1:1 module↔layer correspondence, a self-reinforcing convention a fifth sibling module would break, requiring its own layer membership to be asserted only by doc comment rather than being structurally self-evident like the other four. Nesting under `foundation/` preserves that convention exactly. `ARCH-014` §10 ("the four layers are logically, not physically distinct") permits this without constraint. Foundation's defining property is not "contains only re-exports" as an accident of its first population — it is direct, unmediated reachability of a stable Runtime-adjacent capability, with no replaceable-service indirection (`ARCH-014` §5 item 1). The Observation Client satisfies that property by new code rather than by re-export only because no equivalent public Runtime-side *client* symbol exists to re-export (the Runtime only exposes the *server*-embedding API, `ObservationServiceConfig`/`with_observation_service`) — a distinguishing test it passes on the correct basis: a stable, foundational client contract for an already-established, Founder-approved Runtime capability, not a replaceable service/provider implementation in the `StorageBackend`/`CapabilityAuthority`/`Timer`/`EffectCoordinator` sense (all four of which `foundation.rs` already, individually, and for the identical reason, excludes from re-export).

## 11. Seven-Operation Mapping

Exactly `ARCH-017` §17's seven operations, no eighth, no generic dispatch:

| Foundation Client method (illustrative — not frozen; final naming belongs to implementation-stage SDK-convention review, not this architecture) | Operation | Input | Projection domain (`ARCH-017` §) |
|---|---|---|---|
| `get_runtime_status()` | `GetRuntimeStatus` | none | Reachability, compatibility tier/version (§21) |
| `list_durable_actors()` | `ListDurableActors` | none | Durable actor enumeration (§22) |
| `get_actor_detail(actor_id)` | `GetActorDetail` | `&ActorId` | Identity, lifecycle state (§23) |
| `list_capabilities(actor_id)` | `ListCapabilities` | `&ActorId` | Bound capability projection (§24) |
| `list_effects(selector)` | `ListEffects` | `EffectSelector` (`ByActor(ActorId)` or `ByEffect(EffectId)`) | Effect metadata only, no payload (§25) |
| `get_supervision_relationship(actor_id)` | `GetSupervisionRelationship` | `&ActorId` | `is_registered`/`parent_of` only (§26) |
| `get_diagnostics(actor_id)` | `GetDiagnostics` | `Option<&ActorId>` | Live diagnostic/error information only (§27) |

`EffectSelector` reuses only already-stable, already-Foundation-reachable identity types (`synapse_common::ActorId`, `synapse_effect_coordinator::EffectId`) — no new identity type, no untyped string escape hatch. This is a single input-shape refinement of the sixth operation, matching `ARCH-017` §17's own exact table text ("known `ActorId` (or effect id)") — it does not create an eighth operation; the closed set remains exactly seven throughout this document.

## 12. Public Client Architecture

```rust
// sdk/src/foundation/observation.rs — Foundation Layer, Experimental API tier

pub struct ObservationClient { /* opaque; owns exactly one established session */ }

pub struct ObservationClientConfig {
    pub endpoint: Option<ObservationEndpoint>, // local-only, §20
    pub request_timeout: Option<Duration>,     // provisional, §22
}

pub trait ObservationSource {
    fn get_runtime_status(&self) -> Result<RuntimeStatusView, ObservationClientError>;
    fn list_durable_actors(&self) -> Result<DurableActorsView, ObservationClientError>;
    fn get_actor_detail(&self, actor_id: &ActorId) -> Result<ActorDetailView, ObservationClientError>;
    fn list_capabilities(&self, actor_id: &ActorId) -> Result<CapabilitiesView, ObservationClientError>;
    fn list_effects(&self, selector: EffectSelector) -> Result<EffectsView, ObservationClientError>;
    fn get_supervision_relationship(&self, actor_id: &ActorId) -> Result<SupervisionView, ObservationClientError>;
    fn get_diagnostics(&self, actor_id: Option<&ActorId>) -> Result<DiagnosticsView, ObservationClientError>;
}

impl ObservationClient {
    pub fn connect(config: ObservationClientConfig) -> Result<Self, ObservationClientError>;
    // Establishes a session per ARCH-017 §13's fixed step order. Whether
    // this happens eagerly in the constructor or lazily on first use is
    // an implementation-time decision (§18) — the ORDER of steps is
    // fixed; WHEN the Rust call triggers them is not.
}

impl ObservationSource for ObservationClient { /* the one real, transport-backed implementor */ }
```

No `execute`/`send_raw`/`invoke`/`rpc`/`request(String)` — the seven typed methods, plus `connect`, are the entire public surface. No mutation capability anywhere.

## 13. Projection / DTO Boundary — Semantic Contract vs. Wire Schema

Three conceptual layers, explicitly **not automatically identical**, conversions between them may be required:

1. **Runtime/internal projection representation** — `runtime::observation`'s own `pub(crate)` structs (`EWO-029.1`/`EWO-029.3`'s own, never SDK-reachable).
2. **`EWO-029.5` wire representation** — field encoding, serialization technology, wire-only metadata, framing, optionality encoding, ordering, compatibility representation, protocol versions. Owned entirely by `EWO-029.5`.
3. **SDK/Foundation-facing observation views** (this work order's own `RuntimeStatusView` and siblings) — the semantic SDK contract: what information is available to consumers, its typed meaning, partial/freshness semantics, identities, per-operation result shape.

`EWO-029.4` owns layer 3 only. **`EWO-029.5` MAY choose a wire representation materially different from the SDK-facing Rust view-type layout, provided the semantic contract in layer 3 can be faithfully constructed from it.** No schema-driven format is selected here; the semantic contract, not a wire schema, is what this document normatively fixes.

## 14. Schema Ownership

No schema-driven format is selected. The view types (§12) are the normative *semantic* contract for this stage — never a wire schema (§13). No second, competing source of truth is introduced; `EWO-029.5`'s own eventual wire schema, however expressed, is not pre-empted by this document's Rust type shapes.

## 15. Runtime Dependency Decision

`sdk::foundation::observation` depends on `synapse_common` (for `ActorId`) and `synapse_effect_coordinator` (for `EffectId`) only — both already stable, already Foundation-reachable today. It does **not** depend on `synapse_runtime`: the client is a separate-process consumer (`ARCH-017` §8's own System Context), never embedding or driving a `Runtime`; the one Runtime-side observation symbol, `ObservationServiceConfig`, is server/embedder-facing only, never client-relevant.

Disclosed, not solved here: the existing `synapse-sdk` crate already has an unconditional crate-level dependency on `synapse-runtime` (inherited from Foundation's pre-existing, embedder-facing content, not introduced by this work order), so placing the Observation Client inside the current crate does not, today, reduce Runtime compile/dependency weight for a consumer of `synapse-sdk` as a whole. A future SDK/Foundation crate decomposition may revisit this dependency weight as a separate, later, non-urgent consideration — not scoped or authorized here.

## 16. Transport-Independence Boundary

The public API (§12) exposes zero transport concepts: no socket path, no named-pipe string, no `interprocess` type, no SID/ACL/impersonation detail, no platform-conditional type or method. `ObservationClientConfig.endpoint` is the only transport-adjacent surface, and it is optional and local-only (§20).

## 17. `EWO-029.5` Interface Boundary

`EWO-029.4` requires from `EWO-029.5` exactly: a way to perform `ARCH-017` §13 steps 1–4 given an `ObservationClientConfig`, returning either a live session handle or one of the eight `ARCH-017` §27 error categories; and, given a live session and one of the seven typed requests, a synchronous call returning either a typed response payload (from which this work order's own view types are constructed) or one of the same eight error categories. This document names no serialization, framing, or session wire-representation, and must not be read as implying one — the deliberate handoff boundary `ARCH-017` §31 itself draws.

## 18. Client Lifecycle

`ARCH-017` §13 fixes the *order* of connection-sequence steps; it does not fix *when* the Rust API triggers them. `ObservationClient::connect` **SHOULD** establish the session eagerly, as the simplest, most predictable default — a design recommendation, not an architectural mandate. A lazy, first-use-triggered implementation **MAY** remain valid provided it still performs `ARCH-017` §13's steps in order before any operation proceeds, and still surfaces the same public failure categories (§21). No auto-reconnect, retry-with-backoff, or connection pooling is designed here (`ARCH-017` §31's own Ergonomics-layer exclusion). A dropped/failed connection is not automatically re-established (`ARCH-017` §16/§20: no session continuity exists to make this meaningfully different from constructing a new client). Persistent-vs-per-request connection mechanics are not frozen here — left to `EWO-029.5`/implementation.

## 19. Synchronous / Asynchronous Decision

`ARCH-017` §18 (`ROC-08`) fixes the *protocol-level exchange pattern*: one request produces one response, no streaming — genuinely architecturally fixed. It does not, by itself, fix the *Rust-API shape* of the function that triggers that exchange. `EWO-029.2`'s own filed text: *"a thin, synchronous or async (SDK's own choice, independent of this decision) client... translating wire responses back into typed projections"* — explicit, on-the-record evidence that the Rust-API sync/async question is an open SDK-level choice.

**Decision:** *"Synchronous-first SHOULD be the default `EWO-029.4` implementation direction for simplicity, unless implementation evidence demonstrates a concrete consumer requirement for async."* A design recommendation, not a pre-existing architectural mandate. No async runtime (Tokio, async-std) is introduced at this stage; a future async proposal would need to separately justify the dependency and complexity.

## 20. Endpoint Model and Security Invariant

**Security invariant:** Selecting or overriding `ObservationClientConfig.endpoint` **MUST NOT** bypass the underlying Runtime principal-security model in any way. On Windows, the named-pipe restrictive ACL and same-user SID authorization (`EWO-029.3`, empirically verified, `STOP-07` cleared) apply unconditionally regardless of which endpoint a client targets. On Unix/macOS, Runtime-directory ownership/permissions and peer-principal checks apply unconditionally. An endpoint override changes only *which* local Observation Service endpoint the client attempts to reach — it never grants, weakens, or bypasses access to it.

**Scope:** `endpoint` **MUST** remain local. This work order does not authorize TCP/network addresses, remote hosts, URLs, or any non-local transport target — a future network-capable abstraction, if ever pursued, requires its own separate architectural governance (`ARCH-017` §36).

## 21. `ARCH-017` §15 Endpoint-Discovery Ownership

**Founder decision, recorded at Approval (§42):** `EWO-029.4` owns the user-facing "find/use the default local Runtime" *policy* surface — that `ObservationClientConfig.endpoint: Option<...>` exists, with `None` meaning "use the well-known convention." `EWO-029.5` owns translating the resulting abstract endpoint value into actual connection mechanics (the concrete env-var name, file-handle path, or platform address format — `ARCH-017` §15's own still-open Technology Question, `ROC-06`). This assigns ownership of two already-named surfaces without selecting any wire/session semantics.

## 22. Error Model

Exactly `ARCH-017` §27's eight fixed categories, as a closed Rust enum — no ninth variant, no free-form string as a permanent contract:

```rust
pub enum ObservationClientError {
    ConnectionFailure(/* opaque diagnostic detail */),
    AuthorizationFailure,
    UnsupportedQuery,
    UnavailableInformation,
    RuntimeSideFailure(/* opaque diagnostic detail */),
    CompatibilityFailure,
    MalformedRequest,
    Timeout,
}
```

Per `ARCH-014` §12, this **is** the Foundation layer's own full, truthful, granular error surface, not a simplified developer-facing category set (that distinction applies one layer up, at Ergonomics/Curated Entry, not designed here). `ObservationClientError` must not leak raw Windows error codes, raw `errno` values, `interprocess` error types, or arbitrary Rust error strings as part of its own permanent variant shape; an opaque, non-normative diagnostic string may be attached for human debugging, never part of the compatibility contract. These are semantic SDK errors, not necessarily a one-to-one mapping onto whatever wire error representation `EWO-029.5` internally uses — that mapping is `EWO-029.5`'s own downstream responsibility; the eight categories themselves are fixed and belong to `ARCH-017`/`EWO-029.4`, not renamable or extensible by `EWO-029.5`. Some categories, notably `MalformedRequest`, will rarely if ever originate from a well-behaved client using only these seven typed methods — more likely representing a downstream protocol/mapping defect than an ordinary consumer mistake; the taxonomy itself remains unmodified regardless.

## 23. Timeout Model

`ObservationClientConfig.request_timeout: Option<Duration>` is explicitly provisional: it **MAY** exist only if `EWO-029.5` provides meaningful client-side enforcement for it. If `EWO-029.5` establishes that timeout is entirely server/session-owned (a real possibility — `EWO-029.3`'s own already-implemented `ObservationServiceConfig.read_timeout` is server-side only today), no redundant client-side timeout knob **SHOULD** exist, and this field would be removed rather than retained as dead configuration. Exceeding an enforced timeout surfaces as `ObservationClientError::Timeout`.

## 24. Cancellation Decision

Out of Foundation-layer scope, satisfied trivially: because every operation is synchronous and one-outstanding-request-per-connection (§25), the only cancellation primitive needed at this layer is dropping the `ObservationClient` (or the calling thread), which the transport layer must already handle safely (`ARCH-017` §29's own client-failure-isolation requirement, service side). No explicit cancellation token/future is introduced. An async implementation, if ever justified per §19, would use ordinary `Future` cancellation semantics — no new primitive invented either way. Precise I/O-level cancellation mechanics remain entirely `EWO-029.5`/transport implementation detail.

## 25. Request Correlation / Multiplexing

One outstanding request per connection, matching `ARCH-017` §18's synchronous model and `EWO-029.3`'s own already-implemented one-request-at-a-time production behavior. No request-ID/correlation concept is introduced at Foundation layer. Multiplexing, if ever needed, is `EWO-029.5`'s own decision, not anticipated or foreclosed here.

## 26. Thread-Safety Decision

Not assumed — explicitly deferred to implementation-time verification, per this programme's own hard-won `Runtime: !Send` precedent (discovered only by compiling against the real type, never by assumption, during `EWO-029.3`'s own Windows validation harness work). Architectural intent: `ObservationClient` **SHOULD** be `Send` (it owns only a connection handle, never a `Box<dyn Actor>` or similar Runtime-authoritative state). Whether it is `Sync`/cloneable depends entirely on the concrete connection-handle type `EWO-029.5` selects and must be verified against the real implementation and real target platforms before being documented as a guarantee.

## 27. Partial-Observation Semantics

Every view type (§12) carries the `Complete`/`Partial`/`Unavailable`/`Unsupported` status plus a sequence number, per `ARCH-017` §18's mandatory freshness-metadata rule — precedented by the already-observed, real internal `ObservationMeta`-shaped output (`ObservationMeta { sequence: 0, status: Partial }`) confirmed empirically during `EWO-029.3`'s own Windows validation. "Runtime says there are no results" (`Complete`, empty collection) remains always distinguishable from "Runtime could only provide a partial projection" (`Partial`).

## 28. Identity-Type Handling

`synapse_common::ActorId` and `synapse_effect_coordinator::EffectId` are reused directly — both already stable, already `foundation.rs`-re-exported today, requiring no new identity type and carrying no Runtime-internal structure beyond an opaque identity.

## 29. Security Boundary

The Foundation Observation Client must not: construct its own connection to the Observation Service outside the SDK (`ARCH-017` §10, `ROC-12`); accept, expose, or honor a PID-based identity concept anywhere in its own API; provide any API for selecting "another user's" Runtime endpoint as a privilege-escalation path (§20); disable, bypass, or offer a flag to skip the existing ACL/SID (Windows) or ownership/permission (Unix) checks; introduce any network-reachable transport (§20). `ObservationSource` is explicitly not a security boundary (§31) — only `ObservationClient`, connected through the secured transport path, represents authenticated, authorized Runtime observation. The client is a consumer of the already-secured local Observation Service; it does not replace its security.

## 30. Cross-Platform Assessment

The public API (§12, §18) is, by construction, 100% platform-uniform — zero `#[cfg(windows)]`/`#[cfg(unix)]` code exists anywhere in its public surface. All platform variance (transport mechanism, ACL model) remains entirely beneath the `EWO-029.5`-owned boundary.

## 31. `ObservationSource` / Mockability

`ObservationSource` (§12) is a **public SDK abstraction, intended for dependency injection and testing**. Consumer code **MAY** provide fake/in-memory implementations for their own tests. **`ObservationSource` is NOT a security boundary.** Only `ObservationClient` represents authenticated, authorized Runtime observation; a consumer supplying a custom `ObservationSource` implementation is explicitly choosing a custom data source for their own testing purposes, neither weakening nor interacting with server-side security in any way — code accepting `&dyn ObservationSource` must not assume its caller is talking to a real, secured Runtime. The trait must not expose any method suggesting otherwise (e.g., no `is_authorized()`); its seven methods mirror the seven observation operations exactly, nothing else. `SHOULD`, not `MUST` — `ObservationClient` functions correctly without requiring every consumer to depend on the trait.

## 32. Testing Architecture

**Unit:** typed method → exactly one `ARCH-017` §17 operation, per method. **Error mapping:** each of the eight fixed categories independently exercised. **Projection mapping:** response values → correct view type, correct status/sequence propagation. **Cross-platform:** identical logical assertions run against both a Unix and a Windows transport once `EWO-029.5` exists — not designed or implemented here. **Integration:** real client ↔ real `EWO-029.3` Observation Service, deferred until `EWO-029.5` supplies a concrete transport.

## 33. Language / SDK Scope

Rust-specific, consistent with all four existing SDK layers today. No language-neutral protocol contract is defined here — a non-Rust client, if `EWO-029.5`'s eventual wire format ever permits one, would speak the wire protocol directly, never this crate's Rust types. No Python/JavaScript/C#/Java/Go bindings are designed, implied, or precluded.

## 34. Control Centre Relationship

The future Control Centre is the primary anticipated consumer, but this document names no GUI technology and creates no Control Centre repository. The Foundation Client is designed to be equally usable by CLI diagnostic tooling, developer tooling, or the eventual Control Centre, none privileged over another (`ARCH-017` §8's own "consumer only, never bypasses the SDK" framing; `ROC-17`, general-purpose, never Control-Centre-exclusive).

## 35. Migration / Implementation Implications for `EWO-029.3`

None to `EWO-029.3`'s own production code. `sdk::foundation::observation` is new, additive SDK-side content; `EWO-029.3`'s `runtime/src/observation_service*` files, `parse_request`, `read_bounded_line`, response formatting, the Windows pre-authorization read/watchdog/`CancelIoEx` mechanism, and the existing `WV-P01..WV-P16` regression suite are untouched by this architecture and require no change to support it.

## 36. Acceptance Criteria

**Architecture-stage** (verifiable against this document alone): (1) Foundation-layer placement is structurally coherent with the existing SDK module convention (§10). (2) Seven-operation mapping is complete and matches `ARCH-017` §17's own input specification exactly, including `ListEffects`'s dual input (§11). (3) No Runtime authority is introduced; `sdk::foundation::observation` has zero dependency on `synapse-runtime` (§15). (4) The `EWO-029.5` interface boundary is explicit and selects no wire/session/serialization behavior (§17, §13). (5) The semantic-contract/wire-schema separation is stated explicitly (§13, §14). (6) The endpoint-override and `ObservationSource` security invariants are stated explicitly (§20, §31).

**Implementation-stage** (deferred, verifiable only once code exists): (7) `sdk::foundation::observation` compiles; `ObservationClient` is empirically confirmed `Send` (or explicitly documented otherwise). (8) All seven contract tests pass; `ObservationSource` fake-implementation tests pass.

**Downstream `EWO-029.5`-integration** (explicitly outside this work order's own completion): (9) Real client ↔ real Observation Service integration tests pass once `EWO-029.5` supplies a concrete transport.

## 37. Implementation Sequencing

**Model C — narrow client skeleton first**, explicitly selected. Implementation MAY complete: the public Foundation types (`ObservationClient`, `ObservationClientConfig`, view types, `EffectSelector`); the typed seven-operation `ObservationSource` contract; a fake/in-memory test implementation of `ObservationSource`; the full `ObservationClientError` structure — all without any `EWO-029.5` code existing. Implementation **MUST NOT** pretend complete Runtime connectivity exists before `EWO-029.5` supplies connection/session/compatibility/framing/serialization/wire-mapping — `ObservationClient::connect`'s own real, transport-backed body remains genuinely incomplete (or absent) until then.
