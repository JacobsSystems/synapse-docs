# EWO-029.5 — Connection / Session / Compatibility / Wire-Format Architecture Engineering Work Order

Registered per `GOV-013` (Draft, v0.1.0). This authorizes an Engineering Work Order specification only. It does not itself authorize implementation, and does not amend `ARCH-017`, `ARCH-014`, or any other architecture, standards, or governance document.

## 10. Endpoint Realization

`EWO-029.4` owns the semantic `ObservationEndpoint` policy token (`None` = well-known local-Runtime convention; `Some(token)` = explicit local override). This work order owns translating that logical selection into an actual platform endpoint identifier, and closes `NRR-IIR-029.4-O01` structurally: the realization function cannot produce a network or arbitrary filesystem address because the token is never treated as one.

### 10.1 Logical Endpoint Contract

Logical endpoint identity and physical OS endpoint realization are distinct normative concepts. A valid 128-byte logical token does not imply that all 128 bytes appear literally in a Unix socket filename.

The logical selection is a closed distinction:

- `Default`: no explicit token (`ObservationClientConfig.endpoint == None`);
- `Explicit(token)`: an explicit logical token.

An explicit token **MUST** be non-empty, contain only ASCII letters `A`–`Z`/`a`–`z`, digits `0`–`9`, `_`, and `-`, and contain at most 128 bytes. ASCII letters **MUST** be canonicalized to lowercase before any platform realization. ASCII case-folding does not change byte length. The canonical logical grammar is `^[a-z0-9_-]+$`.

`"Foo"`, `"FOO"`, and `"foo"` identify the same logical endpoint on every platform. `Default` is a distinct variant and is not the explicit token `"default"`. Endpoint selection grants no authority and cannot express a URL, host, port, remote named pipe, or client-selected filesystem path.

### 10.2 Single Executable Authority

A new minimal neutral workspace crate, `synapse-observation-endpoint`, **SHALL** be the sole executable owner of:

- logical token validation and ASCII lowercase canonicalization;
- the `Default`/`Explicit` distinction;
- canonical derivation-input framing;
- Unix/macOS SHA-256 identity and bounded path construction;
- unchanged Windows pipe-name construction; and
- the shared, non-mutating Unix/macOS root-validation routine used by both Runtime and SDK.

Dependency direction is `synapse-runtime -> synapse-observation-endpoint` and `synapse-sdk -> synapse-observation-endpoint`, with no reverse edge and no dependency on `synapse-observation-wire`. Endpoint realization **MUST NOT** be placed in the wire crate, `synapse-common`, Runtime-owned code consumed by SDK, or SDK-owned code consumed by Runtime. Runtime and SDK **MUST NOT** retain independent conforming-looking copies of the mapping or root-validation algorithm.

### 10.3 Canonical Unix/macOS Derivation

The shared authority **SHALL** encode the canonical logical selection into exactly one of these byte strings:

```text
Default:
  b"synapse-observation:endpoint:v1\0default"

Explicit(canonical-token):
  b"synapse-observation:endpoint:v1\0explicit\0"
  || canonical-token.as_bytes()
```

The explicit token is validated and lowercased before its ASCII bytes are appended. The NUL bytes shown above are literal single zero bytes. Because the explicit grammar excludes NUL, framing is unambiguous. The `v1` marker versions local endpoint derivation only; it is not a wire-protocol generation and never appears on the wire.

For every Unix/macOS selection:

1. Construct the exact framed bytes above.
2. Compute SHA-256 over those bytes.
3. Encode all 32 digest bytes as exactly 64 lowercase hexadecimal ASCII characters.
4. Produce the filename `o-<64-lowercase-hex>.sock`.

The framed-byte specification above is normative. The following known-answer vectors are also normative conformance vectors derived from those exact bytes; they do not replace or reinterpret the framed-byte specification, and they **MUST** agree with it:

| Logical selection | Exact framed-input length | SHA-256 (64 lowercase hexadecimal characters) |
|---|---:|---|
| `Default` | 39 bytes | `0344871931be4acac880bf9dc3632b2a8182cadace32d260d80c869c3132a04e` |
| `Explicit("foo")` | 44 bytes | `41a82fc3a7d5b5ba63c35d765aba8b29ac85d7d3107714ffc44f9733403c7aaf` |

The input lengths count each displayed `\0` as one literal zero byte, never as textual backslash-plus-zero characters. The vectors are platform-independent. An implementation that produces any different digest for either canonical selection is non-conforming.

There is no token-length threshold, direct-name fast path, truncation, random salt, process identifier, environment value, registry, lookup table, suffix retry, or mutable state. Rust `DefaultHasher` is prohibited because Rust does not specify its algorithm as a durable cross-release identity contract.

### 10.4 Bounded Per-User Root

On Unix/macOS, the literal pathname supplied to the local-socket layer **SHALL** be:

```text
/tmp/synapse-u<euid-as-8-lowercase-hex-digits>/o-<64-lowercase-hex>.sock
```

The effective UID is represented as exactly eight zero-padded lowercase hexadecimal digits, covering the supported platforms' 32-bit `uid_t`. `TMPDIR`, `std::env::temp_dir()`, checkout location, home directory, current directory, token length, process ID, and arbitrary environment values **MUST NOT** influence the root or pathname.

The literal `/tmp` spelling **MUST** be passed to the local-socket layer and **MUST NOT** first be canonicalized to a longer spelling. A platform-provided `/tmp` indirection, such as macOS's system-managed parent mapping, does not authorize following or accepting a substituted final per-user component. There is no alternate or unbounded fallback root.

### 10.5 Shared Root-Validation Contract

The final per-user root is part of the endpoint-integrity boundary, not merely a placement convenience. The shared root validator **MUST** be non-mutating and, using no-follow semantics for the final component, establish all of the following about the same root object that will be used for bind or connect:

1. the root exists;
2. the final component is a real directory, not a symlink or other object;
3. its owner UID equals the calling process's effective UID;
4. its permission bits are owner-only `0700`-class, with no group or other access; and
5. no attacker-controlled final-component substitution can invalidate the ownership/type result before use.

Any inability to establish those facts is an endpoint-creation or connection failure and **MUST** fail closed.

### 10.6 Runtime Root Creation and Validation

Runtime alone may create the final per-user directory. Runtime **MUST** distinguish a directory atomically created by the current Runtime instance from any root that already existed; it may not collapse those states into a repair path.

**Newly created root.** When the final component is absent, Runtime may attempt atomic creation with owner-only permissions. Exact `0700` permission establishment is permitted only as part of that successful new-root creation flow, before the directory is exposed for or used by any Observation endpoint operation. Runtime **MUST** then pass the same newly created object through the shared non-mutating validator, proving that it is a real non-symlink directory, is owned by the effective UID, has exact owner-only permissions, and cannot be substituted before use. Only after validation succeeds may Runtime clean up or bind an endpoint inside it. Failure of any predicate fails closed.

**Pre-existing root.** Any root that already exists is untrusted input, including a root whose owner UID equals the effective UID. Before endpoint cleanup, bind, or any other use, Runtime **MUST** apply the shared non-mutating validator and require the pre-existing root already to be a real non-symlink directory, already to be owned by the effective UID, and already to satisfy the exact private owner-only permission predicate. If any predicate fails, Runtime **MUST** fail closed.

Runtime **MUST NOT** chmod, chown, delete, replace, rename over, take ownership of, normalize, repair, or fall back from any pre-existing invalid root. In particular, a pre-existing same-owner but wrong-mode root **MUST NOT** transition through `wrong mode -> chmod 0700 -> trusted root`. If a directory was previously group/other-accessible, restricting its permissions later cannot establish the provenance of contents that may already have been planted inside it; technical ability or current ownership does not make repair safe. Privileged operational cleanup is outside this endpoint protocol.

Existing verified-dead stale-socket reclamation may occur only inside a pre-existing or newly created root that has passed the shared validator without mutation. No blind deletion, legacy-path cleanup, alternate directory, or legacy realization fallback is authorized.

### 10.7 SDK Pre-Connect Validation

SDK does not create or repair the root. Before attempting a Unix/macOS socket connection, SDK **MUST** call the same shared root validator and proceed only after validation succeeds. If the root is absent, a symlink/non-directory, owned by another UID, has group/other access, or cannot be validated without following an attacker-controlled final component, the SDK **MUST** return `ObservationClientError::ConnectionFailure` and **MUST NOT** attempt the socket connection.

On validation failure, SDK **MUST NOT** delete, chmod, chown, take ownership of, replace, or repair the root; choose another root; use an environment-derived path; fall back to the legacy direct-name path; or connect anyway. Runtime creates and validates; SDK validates only. Both enforce the same root predicate through the same executable authority.

### 10.8 Root-Squatting Availability Residual

A different local user may pre-create the predictable per-effective-UID root before the legitimate user and thereby cause Runtime and SDK validation to fail. A pre-existing same-owner root with non-private permissions is equally invalid because its existing contents have no recoverable trusted provenance. The required response is fail-closed denial of service. This availability residual is explicitly accepted in preference to unsafe recovery. Neither consumer may delete the invalid directory, take ownership, change its permissions, replace it, select an unapproved fallback, or revert to the legacy path. Operational or privileged cleanup is outside this endpoint protocol and grants no implementation discretion to weaken validation.

### 10.9 Complete Path-Length Proof

All pathname components are ASCII and therefore one byte each:

| Component | Pathname bytes |
|---|---:|
| `/tmp` | 4 |
| `/` | 1 |
| `synapse-u` | 9 |
| fixed-width effective UID | 8 |
| `/` | 1 |
| `o-` | 2 |
| full SHA-256 lowercase hex | 64 |
| `.sock` | 5 |
| **Complete pathname** | **94** |

`interprocess` checks pathname length against the actual `sun_path` array and writes a terminating NUL. Therefore:

| Platform | Pathname | NUL | Occupied `sun_path` bytes | Capacity | Remaining margin |
|---|---:|---:|---:|---:|---:|
| macOS | 94 | 1 | 95 | 104 | 9 |
| Linux | 94 | 1 | 95 | 108 | 13 |

The NUL lies inside the array at index 94. The proof covers `Default`, every explicit token length from 1 through 128 bytes, and every 32-bit effective UID. Only digest input length changes; the pathname does not.

### 10.10 Collision Semantics

SHA-256 is finite; mathematical uniqueness is not claimed. Full 256-bit output provides negligible practical collision probability. A collision would map two logical selections for the same effective UID to one Unix endpoint. No registry or alternate-name retry is added. A competing bind follows the existing endpoint-in-use failure path; there is no silent second endpoint or fallback. The digest is identity derivation, not a secret, credential, authorization token, or confidentiality mechanism.

### 10.11 Runtime Configuration Boundary

The current public `ObservationServiceConfig.endpoint_dir` and `pipe_name` fields expose physical naming authority, while SDK accepts a logical selection. That conflation is incompatible with one canonical mapping. The separately authorized implementation correction **MUST** replace the production public physical selection fields with the same logical `Default`/`Explicit(token)` distinction and route it through `synapse-observation-endpoint`.

No production public configuration may independently select an arbitrary Unix directory, Unix filename, or Windows pipe name. A crate-private or test-only transport fixture may inject a physical path only if it is structurally unavailable to production consumers and cannot become a second public authority. The exact idiomatic Rust constructor/builder shape is an implementation decision; the single logical authority is not.

This is a breaking Runtime source-configuration change and triggers `STOP-029.6-02` for separate Founder implementation authorization. `ObservationClientConfig`, `ObservationEndpoint`, and the 128-byte logical contract remain unchanged.

### 10.12 Compatibility and Migration

## 11. Connection Lifecycle

Persistent-vs-per-request connection choice is left open, per `EWO-029.4` §18's own already-approved deferral — this work order's own compatibility design (§13) imposes no preference either way: folding compatibility validation into a connection's first request saves one dedicated round-trip *per connection*, a benefit realized identically regardless of how many requests that connection goes on to carry. Connection failure (no listener, wrong endpoint, refused) maps to `ObservationClientError::ConnectionFailure`. Graceful and abnormal close are treated identically (unchanged from `EWO-029.3`'s own existing behavior). No automatic reconnection exists at this layer.

## 12. Session Model

**Minimal — the connection itself is the session**, per `ARCH-017` §16's own text: a session "carries exactly one fact... no session state persists across reconnection." No session ID is introduced; none is architecturally justified, since no differentiated permission level exists for one to distinguish. The one fact a Phase-1 session carries, precisely: *this connection's first request presented a supported protocol generation, recorded as this connection's established generation for its own remaining lifetime.*

## 13. Compatibility Model

**Terminology, reconciled against `ARCH-017` §19 precisely:** this is **Compatibility Presentation and Validation**, not two-sided range negotiation. `ARCH-017` §19 anticipates each side presenting "tier and version-range information"; this protocol's v1 simplification is that each side presents exactly one generation number (a degenerate range of size one) — the server's `protocol_version` field, present on every response, constitutes its own side of "presenting," satisfying the requirement in its simplest legitimate form rather than reinterpreting it away.

**Permanent protocol invariant, binding on every future generation:** the JSON key `protocol_version` (type `u32`) **MUST** appear as a top-level key in the *first* line of every connection, in every generation, forever — the one piece of wire shape that must never change, making the version probe itself version-stable regardless of how later generations otherwise reshape their own request bodies.

**Two-phase parse.** Phase 1: the server deserializes the first line's bytes *only* as a minimal version-probe shape (`protocol_version: u32`, all other fields ignored, unknown-field-tolerant), extracting the generation without interpreting operation semantics or dispatching. Phase 2, only if Phase 1's generation is supported: the server re-parses the *same, already-read* line as that generation's full operation-request shape. An unsupported version halts at Phase 1 — Phase 2 never runs.

**First-request-only version establishment.** `protocol_version` appears *only* in the first request of a connection; subsequent requests on the same connection carry no such field at all — the generation is already established for the connection's remaining lifetime, and a missing field structurally eliminates any question of what happens if a later request's version were to differ from the first's.

**Corrected compatibility sequence, precisely:**

1. Acquire the first request as one bounded raw line. Unix/macOS: authorize the peer principal (`peer_creds`) *before* this read. Windows: this read *is* the pre-authorization read — no semantic interpretation of its bytes occurs yet.
2. Windows only, at this point: authorize (impersonate the client, extract and compare SID, `RevertToSelf`).
3. Parse the already-acquired line's bytes as the version probe only (Phase 1) — no operation interpretation.
4. Validate the extracted generation. Unsupported ⇒ the pre-version error envelope (§20), carrying the server's own current/maximum supported generation, connection closes. Supported ⇒ continue.
5. Establish the connection's session generation (§12).
6. Re-parse the same line's bytes as a full generation-1 operation request (Phase 2).
7. Dispatch and respond, the established generation carried on the response.
8. Loop: every subsequent request is read, parsed directly as an operation request (no probe phase, no `protocol_version` field expected), dispatched, and responded to identically until connection close.

Unix and Windows differ *only* in step 2's presence/timing relative to step 1 — unchanged from `EWO-029.3`'s own already-empirically-validated behavior.

## 14. Windows Pre-Authorization Read — Explicit Normative Rule

**On Windows, no JSON deserialization, version-probe parse, operation parse, or any semantic interpretation of any kind MAY occur before successful SID authorization.** Before authorization, only a bounded raw-byte/line read (framing acquisition) is performed — the bytes are held as an opaque buffer, re-parsed only after authorization succeeds. This is a binding implementation-acceptance gate, not merely narrative intent, and applies equally regardless of whether decoding is performed by hand-written code or by the neutral wire crate's own decode helpers (§18) — the rule concerns *when* decoding may occur, not *which code* performs it. Unix/macOS continues to authorize before any read at all, unchanged.

## 15. Protocol Versioning

Single unsigned integer generation number (`protocol_version: u32`), not major.minor — the entire wire schema is small and versioned as one indivisible unit. Starting value: `1`. `0` is permanently reserved as the "not established" sentinel (§20) and is never allocated to a real generation. Compatible/additive change (no version bump required): a new optional field on an existing payload, ignored by older readers. Breaking change (requires a version bump): removing/renaming a field, changing a field's type or meaning, adding an eighth operation (which additionally requires a separate `ARCH-017` amendment), or removing an error category. Unsupported version ⇒ `CompatibilityFailure`, connection closed.

## 16. Serialization and Framing

**Serialization: JSON, via `serde`/`serde_json`.** Selected over CBOR, MessagePack, Protocol Buffers, and `bincode` after explicit candidate analysis weighing language neutrality, schema-evolution tolerance, parser maturity, debuggability, dependency weight, determinism, payload size, and — critically — Rust-coupling risk: `bincode`'s own positional, non-self-describing encoding would make the wire protocol "Rust ABI/serde-layout by another name," the exact anti-pattern this work order explicitly rejects. Given this is local, low-throughput, small-payload observation traffic (`EWO-029.3` §32's own "local developer-platform infrastructure" framing), debuggability and dependency-maturity outweigh binary compactness; the existing `max_response_bytes` bound (§22) already caps payload size regardless of format.

**Framing: JSON Lines — one compact (non-pretty-printed) JSON object per newline-delimited line.** Compact `serde_json` output cannot contain a raw, unescaped `\n` byte (an embedded newline inside a JSON string is escaped as the two-character sequence `\n`), so `EWO-029.3`'s existing, already-Windows-validated bounded-line-read primitive remains exactly correct — this framing choice requires zero change to that primitive's own bound/EOF/oversized-input handling, and in particular requires no re-validation of the Windows pre-authorization I/O-activity-trigger mechanism (§14), since only the *content* interpretation of an already-read line changes, never the read's own timing or bound.

## 17. Wire Schema Ownership — Neutral Crate

**Architecture decision only — the crate is not created by this work order.** A new, minimal crate, **`synapse-observation-wire`**, is the sole owner of the wire protocol contract.

**Contains:** the version probe; the bootstrap/pre-version error envelope; the generation-1 operation-request enum and argument shapes; `EffectSelector`'s wire form; the response envelope and outcome types; the six-member `WireErrorCategory`; per-operation wire payload structs; small wire-owned mirror enums for `ActorState`/`RuntimeState`/`AttemptStatus` (avoiding any dependency on `synapse-common`/`synapse-effect-coordinator`); protocol-generation constants; and thin, pure encode/decode helper functions (§18).

**Does not contain:** any Runtime logic, SDK behavior, transport/connection code, authorization, dispatch, session lifecycle management, or business logic of any kind. Zero `unsafe`. Zero I/O.

**Identity encoding, zero domain dependency:** `ActorId`/`EffectId`/`EffectAttemptId` are represented on the wire as plain, opaque, unconstrained `String`s — the domain types themselves impose no format constraint today, so the wire layer inherits that identical lack of constraint rather than inventing a new one. This achieves genuine, dependency-graph-verifiable neutrality: **`synapse-observation-wire` depends on nothing but `serde` and `serde_json`.**

**Dependency direction:** `synapse-runtime` → `synapse-observation-wire`; `synapse-sdk` → `synapse-observation-wire`; `synapse-observation-wire` → (`serde`, `serde_json` only). No edge from the wire crate to either consumer — cycle-free by construction. **`synapse-runtime`'s own public re-export surface MUST NOT be broadened merely to expose wire DTOs** — `runtime` consumes the wire crate as an ordinary, private-to-its-own-implementation dependency for its `to_wire()` conversions; nothing about this requires any new `pub use`/`pub mod` in `runtime/src/lib.rs` or `sdk/src/foundation/mod.rs`. The public Foundation semantic API (`sdk::foundation::observation::*`) remains entirely `EWO-029.4`-owned and untouched.

**Schema authority, singular and explicit:** the versioned DTO definitions and serialization rules implemented by `synapse-observation-wire` are the sole authoritative executable protocol schema. Human-readable protocol documentation and golden JSON fixtures are required derived conformance artifacts — they MUST accurately describe, and remain consistent with, that authoritative schema, but MUST NOT override it or serve as an independent, competing source of truth. Golden fixtures MUST be mechanically, automatically verified against the wire crate's own actual encode/decode behavior (fixture-decodes-to-expected-DTO; DTO-encodes-to-canonical-fixture-bytes where determinism is claimed; round-trip where applicable) — not left to manual maintenance discipline. `STOP-029.5-12` (§Engineering Stops) governs any discovered disagreement among these three artifacts, or a proof that the mandatory error envelope (§22) cannot fit under a valid configuration — an engineering/build/test/review-time discipline only, never something a running server process itself executes.

## 18. Wire Encode/Decode Ownership

`synapse-observation-wire` owns thin, pure encode/decode helper functions in addition to its bare type definitions — a single implementation boundary preventing `runtime` and `sdk` from independently hand-rolling `serde_json` call sites with potentially divergent options. These helpers MAY perform: compact JSON serialization/deserialization for every wire type; version-probe decoding; the `sequence` decimal-string ↔ `u64` mapping (§25); base/bootstrap error-envelope encoding. They MUST NOT perform: any I/O (no socket/pipe access); authorization; Runtime dispatch; SDK semantic conversion. Every encode helper MUST produce compact (non-pretty-printed) JSON, guaranteeing the JSON-Lines no-raw-newline property by single implementation, not by convention repeated independently in two crates.

**Framing ownership, cleanly separated:** the transport/service/client layer (unchanged `EWO-029.3` machinery) owns reading/writing one bounded line, timeouts, and connection close. `synapse-observation-wire` owns only the JSON content *inside* an already-acquired line — it never touches a socket or pipe directly.

## 19. Seven-Operation Wire Mapping and `EffectSelector`

The wire operation enum maps one-to-one to `ARCH-017` §17's seven closed operations and `EWO-029.4`'s own `ObservationSource` trait: `GetRuntimeStatus`, `ListDurableActors`, `GetActorDetail { actor_id }`, `ListCapabilities { actor_id }`, `ListEffects(selector)`, `GetSupervisionRelationship { actor_id }`, `GetDiagnostics { actor_id: Option<String> }`. No eighth variant; an unrecognized operation tag fails deserialization structurally, with no generic fallthrough. `EffectSelector` preserves both `ByActor`/`ByEffect` forms as a single tagged wire shape, reaching one `ListEffects` operation, never two.

## 20. Message Envelope

**Bootstrap layer** (permanently stable, generation-independent, used at most twice per connection — the version probe on request 1, and, only on failure, the pre-version error response): the version probe (`protocol_version: u32`, all else ignored) and the pre-version error envelope (`protocol_version` — `0` for "not established," or the server's own current generation for a version mismatch — plus a fixed `outcome`/`body` error shape).

**Generation-1 layer:** the operation-request shape (no `protocol_version` field, per §13); the response envelope (`protocol_version`: the connection's established generation, carried on every response; `outcome`: `Ok`, with a payload shape implied by the request's own operation, or `Err`, carrying a `WireError`).

**Canonical `outcome` spelling, stated explicitly (`v0.3.0` clarification).** The serialized JSON value of the `outcome` discriminator, in both the bootstrap and generation-1 layers above, is exactly `"Ok"` for a successful outcome and `"Err"` for an error outcome — matching, without exception, the literal, case-preserving convention this document already applies to every other closed wire-tag vocabulary (§19's operation tags; §23's `WireErrorCategory` names), none of which undergo any case transformation on the wire. Lowercase `"ok"`/`"err"` is not a valid generation-1 spelling and MUST NOT be emitted by an encoder; a generation-1 decoder MUST NOT accept it as an alias. This clarifies wording that was previously open to two readings (a literal wire-tag spelling, consistent with this document's own convention elsewhere, versus a Rust/conceptual-only name) — it introduces no new field, no new state, and no protocol-generation change. The bootstrap layer's own `outcome` vocabulary remains exactly as stated above: `"Err"` only; the bootstrap layer carries no success case and this clarification does not introduce one.

This is deliberately not a framework for arbitrary version families — a future generation 2 would define its own generation-2 shapes while the bootstrap layer's own permanent contract (the fixed `protocol_version` key) remains unchanged forever.

## 21. Runtime Projection ↔ Wire ↔ SDK Semantic Mapping

Three layers, strictly separated, none forced to equal any other's layout: (1) the seven existing, wholly unmodified `EWO-029.1` Runtime-internal projection functions remain the sole truthful observation source; (2) `runtime`'s own `to_wire()` conversions, one per operation, build the corresponding wire payload and perform the response-capacity check (§22 below); (3) `sdk`'s own conversions, one per operation, build the corresponding `EWO-029.4` semantic view from a decoded wire payload. Wire DTO field names/shapes are free to differ from both neighbors.

## 22. Response Bound and `Partial` Semantics

**`ObservationStatus::Partial` remains reserved exclusively for genuine Runtime-observed partiality** ("Runtime itself could only provide a partial observation") — it MUST NOT be produced or reinterpreted to mean "transport could not fit the complete observation." Capping for wire-capacity reasons lives entirely in the wire-conversion layer (§21, item 2), strictly downstream of the unmodified projection functions, never inside them. If a fully-formed semantic response cannot fit inside `max_response_bytes`, the server returns `WireError{category: UnavailableInformation}` — no pagination, no wire-specific truncated representation. A genuinely `Partial` Runtime result that happens to fit within the bound is transmitted as `Partial`, exactly as produced; a `Complete` Runtime result too large to fit becomes `UnavailableInformation`, never silently relabeled.

`max_request_bytes` remains a configurable default, unchanged at 4096 bytes, enforced before any JSON parsing is attempted.

`max_response_bytes` **MUST be configured to at least 512 bytes**; a configuration below this floor MUST be rejected by the Observation Service at startup/config validation. This is a conservative floor (fixed JSON envelope overhead plus the 256-byte diagnostic-detail ceiling plus a JSON-escaping-expansion safety margin), guaranteeing — precisely — that the *detail-free mandatory error envelope* fits. It does **not** guarantee that every detail-bearing error envelope fits, since JSON escaping can in principle expand a 256-byte diagnostic string substantially; the detail-bearing form is therefore the preferred, best-effort diagnostic form, never assumed unconditionally safe, which is exactly why the fallback below is mandatory, not defensive-only.

**Error-envelope encoding, deterministic and bounded:** (1) construct and encode the error with its diagnostic `detail` present (≤256 UTF-8 bytes, boundary-safe); if it fits, send it. (2) If it does not fit, omit `detail` entirely and encode the mandatory detail-free form; given `max_response_bytes ≥ 512`, this MUST fit, and is sent. (3) **Residual runtime action, if the detail-free form somehow still does not fit despite a validly-configured bound:** the Observation Service MUST close the connection without writing any response — no plaintext, no malformed or partial JSON, no further retry. This is the same, already-established "close without response" pattern this document uses elsewhere (an ambiguous zero-byte close; a mid-session drop), not a new wire behavior. Client interpretation: `ObservationClientError::ConnectionFailure`, unless the client's own `request_timeout` had already fired first (then `Timeout`) — no new SDK or wire category. Separately, and distinctly from that one-line runtime action: reaching this residual case under a validly-configured deployment is classified as an implementation defect or schema divergence and MUST fail implementation tests/block release (`STOP-029.5-12`) — a build/test/review-time invariant, never itself "executed" by the running server.

`WireError.detail`, at every layer, is optional, diagnostic, non-normative, and MUST NOT carry compatibility-significant meaning — no consumer may parse or branch on its exact text.

**Every response actually written to the wire remains valid JSON, without exception, at every stage of this document's own lifecycle** — no legacy plaintext response survives anywhere; silent connection closure (writing nothing) is the sole permitted alternative when no valid response can be produced.

## 23. Error Model

**Wire-transmitted (`WireErrorCategory`), exactly six:** `UnsupportedQuery`, `UnavailableInformation`, `RuntimeSideFailure`, `CompatibilityFailure`, `MalformedRequest`, `Timeout`. `RuntimeSideFailure` is reserved exclusively for the case the server itself explicitly reports — never reused for a client-side decode failure. `UnsupportedQuery` is defined and reserved for forward compatibility (a syntactically valid, recognized operation the current Runtime/service build cannot presently satisfy) even though no concrete v1 trigger currently exists for it — its absence of a current use is disclosed honestly, not manufactured a use to justify its existence.

**Client-local only (never wire payload values):** `ObservationClientError::ConnectionFailure` and `AuthorizationFailure` remain part of `EWO-029.4`'s own eight-category semantic taxonomy but are synthesized locally from connection-level evidence, never transmitted:

| Source | Wire/OS condition | SDK semantic error |
|---|---|---|
| Windows pipe-open `ERROR_ACCESS_DENIED` | local OS, pre-stream — the sole reliable basis | `AuthorizationFailure` |
| Endpoint absent / connection refused | local OS | `ConnectionFailure` |
| Post-connect zero-byte close, no exchange yet succeeded | local OS/transport, ambiguous | `ConnectionFailure` |
| Established connection drops mid-session, after ≥1 successful exchange | local OS/transport, ambiguous | `ConnectionFailure` (unless local timeout already fired → `Timeout`) |
| Malformed / structurally invalid / undecodable response (any cause, including an invalid or overflowing `sequence`) | client-side decode failure | `ConnectionFailure` |
| Residual "mandatory error envelope still cannot fit" close (§22) | local, no response ever sent | `ConnectionFailure` (unless local timeout already fired → `Timeout`) |
| Client's own `request_timeout` expires while awaiting a response | local, no wire message involved | `Timeout` |
| Wire `UnsupportedQuery` / `UnavailableInformation` / `RuntimeSideFailure` / `CompatibilityFailure` / `MalformedRequest` / `Timeout` (validly decoded) | server, transmitted | identical name |

`ConnectionFailure`'s ambiguous-close uses are an explicitly accepted limitation, not resolved away: this signal cannot reliably distinguish authorization rejection from Runtime crash, shutdown, resource exhaustion, or generic transport failure, and `EWO-029.3`'s own already-approved "disclose nothing beyond ordinary connection closure" security property forecloses making it more specific. On Unix/macOS, this is the *only* rejection path — no OS-level equivalent to Windows's `ERROR_ACCESS_DENIED` exists.

**No ninth SDK category, no seventh wire category is introduced anywhere in this document** — `EWO-029.4`'s own closed eight-category taxonomy is respected throughout, never unilaterally extended.

## 24. Malformed Input, Unknown Fields, Unknown Operations

Unknown JSON fields are ignored (not rejected) on every structural payload — `serde`'s own default behavior, deliberately not overridden — the explicit forward-compatibility mechanism; the closed tag vocabularies (`op`, `outcome`, `category`) remain non-extensible regardless. An unrecognized operation tag fails deserialization structurally and maps to `MalformedRequest` — defensible precisely because, once a connection's generation is established (§13), that generation's own operation vocabulary is fixed; a recognized-generation-but-unrecognized-operation combination can only arise from genuine malformation, never from legitimate version skew (which is already caught earlier, at the version-probe phase). An oversized request line (exceeding `max_request_bytes`) is rejected before any JSON parsing is attempted; the server MAY best-effort write the fixed pre-version `MalformedRequest` envelope (§20) before closing. A truncated request (EOF with a non-empty partial line) receives identical treatment; an EOF with an empty buffer remains a silent, clean disconnect.

## 25. `sequence` (`u64`) Wire Representation

Encoded as a decimal-digit JSON *string* (not a number), preserving the full `u64` range without ambiguity for any JSON parser — including those (e.g. naive JavaScript `JSON.parse`) that cannot exactly represent integers above `2^53 − 1`. Canonical form: no leading sign, no unnecessary leading zeros, `"0"` exactly for zero. Malformed (empty, non-digit, signed, or `> u64::MAX`) is treated identically to any other undecodable-response case (§23) — `ConnectionFailure`, since `sequence` appears only in responses and a malformed value is discovered entirely client-side. This transformation applies only to `sequence`; `protocol_version` and `retry_max_total_attempts` (both `u32`) remain ordinary JSON numbers, safely within every mainstream JSON parser's exact-integer range.

## 26. Request Correlation and Multiplexing

No `request_id` in v1: one outstanding request per connection, matching `EWO-029.3` §24's already-approved connection model and `ARCH-017` §18/`ROC-08`'s protocol-level exchange pattern — with strictly sequential request/response pairs on a single connection, response-N unambiguously corresponds to request-N by construction. Multiplexing is not pursued; a future need for concurrent queries (e.g. from a Control Centre, unbuilt) is met by opening multiple connections, not by multiplexing within one.

## 27. Cancellation

No dedicated wire cancellation operation. With one synchronous outstanding request per connection, dropping the connection is cancellation — the transport layer already handles this safely (`ARCH-017` §29).

## 28. Streaming

**No.** All seven operations remain request/response. No subscriptions, watches, event feeds, or server push. A future streaming capability, if ever separately governed, would require its own protocol-generation bump and architecture amendment — this document forecloses nothing about how that would work, only confirms it does not exist in v1.

## 29. Determinism and Debuggability

Every wire type defined by this architecture is a plain struct/closed-enum/array — no unordered map/object collection appears anywhere a deterministic output matters; a future addition to the wire schema SHOULD preserve this property. JSON Lines traffic is directly inspectable with any text tool — no binary decoder is ever required, matching this workspace's own explicit debuggability priority for an actively-evolving system. No security property relies on traffic being hard to read; authorization is entirely OS-level, prior to any byte having semantic meaning.

Endpoint identity is independently deterministic under §10: fixed domain-separated input bytes, SHA-256, full lowercase hexadecimal output, a fixed per-effective-UID root, and no process-randomized hash, environment value, registry, or mutable state. Runtime and SDK consume the same executable authority and known-answer vectors; independent derivation implementations are non-conforming.

## 30. Cross-Platform and Cross-Language Assessment

The application-level wire protocol is identical on Windows and Unix/macOS — only authorization *timing* relative to the first read differs (§13), unchanged from `EWO-029.3`'s own already-established, empirically-validated asymmetry. No `#[cfg(windows)]`/`#[cfg(unix)]` distinction exists anywhere in the wire schema itself. JSON Lines is fully language-neutral by construction; **Rust source alone is not claimed sufficient documentation for a non-Rust consumer** — the required human-readable protocol documentation and golden fixtures (§17) exist precisely to serve that need, distinct from (and not weakened by) the wire crate's own authoritative-schema status.

## 31. Dependency Strategy

`serde` (`derive` feature) and `serde_json`, added to the new `synapse-observation-wire` crate at implementation time only — not added by this architecture-stage document. Concrete versions, MSRV compatibility, license, feature set, and transitive footprint MUST be explicitly verified immediately before that addition. `sdk` gains access to the wire crate's own types through a new, symmetric dependency edge, not through its pre-existing `synapse-runtime` dependency (which remains, unrelated to this work order, for `EWO-029.4`'s own Foundation-layer re-export purposes).

The current workspace contains no suitable specified-stability cryptographic hash facility, and Rust's standard library supplies none. Lowercase hexadecimal encoding is trivial and **SHALL** be implemented without a separate encoding dependency unless implementation evidence proves that unsafe or impractical. The endpoint crate may use the workspace's existing Unix `libc` facility to obtain the effective UID and validate ownership metadata.

Before addition, implementation review **MUST** record the selected `sha2` version, exact feature set, MSRV compatibility, license, transitive footprint, lockfile change, advisory status, and SHA-256 known-answer tests. No dependency is added by this Review candidate.
