## 1. Purpose

`ARCH-014` establishes the permanent, four-grouping architecture of the Synapse SDK — Foundation, Ergonomics, Curated Entry, Extension — but before this work order, none of it existed in `synapse-runtime`. This work order implements the constitutional skeleton only: the crate itself, the four module boundaries, and real, working re-exports for exactly one grouping (Foundation), per `ARCH-014` §5's own definition that Foundation "adds nothing and removes nothing — it is the SDK's floor." No developer ergonomics, prelude content, extension mechanism, CLI, or example application is introduced.

---

## 2. Architectural Authority

Every structural decision in this work order traces directly to `ARCH-014`:

- The four-`pub mod` crate structure realizes `ARCH-014` §5's own four named groupings.
- `foundation.rs`'s use of named re-exports, never `pub use synapse_runtime::*`, and its explicit exclusion of `TrustedCore`, directly implements `ARCH-014` §8's Public API Architecture (the `TrustedCore` precedent `DPP-001` §4 and `ARCH-013` §13 already establish) — a glob import would have silently reintroduced the exact defect those documents identified.
- `ergonomics.rs`, `prelude.rs`, and `extension.rs` remain empty, doc-commented boundaries — populating any of them is explicitly excluded by this work order's own Scope, and remains future, separately authorized engineering under the same `ARCH-014` §5 definitions these modules already cite.
- The module named `prelude` (not `curated_entry`) rests on a disclosed interpretation of `ARCH-014` §9 ("Prelude... names one possible future implementation realization" of the Curated Entry Layer concept) — not an unambiguous citation, recorded as such in the module's own doc comment.

---

## 3. Objectives

1. Create the `synapse-sdk` crate at the workspace's top level, correctly registered in `Cargo.toml`.
2. Establish the four module boundaries `ARCH-014` §5 requires.
3. Populate `foundation` with real, complete, individually-justified re-exports of the Runtime's own already-public operational surface — checked, on Independent Engineering Review, against every `pub` item in every dependency crate individually, not merely against an intended list.
4. Leave `ergonomics`, `prelude`, and `extension` as empty boundaries.
5. Prove Foundation's own genuine usability — not merely its compilability — through integration tests exercising a full actor lifecycle (including durable checkpoint and independent recovery) and a capability-denial path, using only `synapse_sdk::foundation`'s own re-exports.

---

## 4. Non-Goals

This work order MUST NOT, and its implementation does not:

- populate `ergonomics`, `prelude`, or `extension` with any real convenience, curated re-export, or extension mechanism;
- introduce any macro, builder, CLI, project template, or example application;
- redesign any Runtime, Persistence, Recovery, Scheduling, or Capability behavior (confirmed: no Runtime `.rs` source file appears in this work order's own diff, at any stage, independently re-verified by the Independent Engineering Re-Review);
- modify any existing crate's own `Cargo.toml` beyond the workspace root's own two-line registration;
- introduce a Public API Architecture tier-marking mechanism — explicitly deferred by `ARCH-014` §21 itself.

## 6. Required Test Coverage

`sdk/tests/skeleton.rs` — two integration tests, deliberately placed as automated structural verification rather than a developer-facing example (the identical distinction `runtime/examples/actor_to_actor_messaging.rs` and `runtime/tests/actor_to_actor_messaging.rs` already establish for the same scenario), exercising `synapse_sdk::foundation` exclusively from outside the crate:

- `foundation_layer_supports_a_full_actor_lifecycle_including_durable_recovery` — bootstrap, actor definition and creation, message submission and execution, durable checkpoint, Runtime shutdown, and independent recovery via a freshly-opened backend — proving Foundation's own reachability is genuine, not merely compilable.
- `foundation_layer_reports_capability_denial_truthfully` — proves the Runtime's own structural, non-ambient capability enforcement (`ARCH-001` §5.2) remains intact and observable through the Foundation Layer.

Not a Hello Durable World example (`ARCH-014` §17), which remains explicitly out of this work order's own scope and a distinct future deliverable.

## 7. Engineering Amendment Record — Finding F01

An Independent Engineering Review of the original implementation found one Minor finding: two meaningful, Runtime-operation-relevant `pub const` items — `MAX_BOOTSTRAP_GRANTS` (`synapse-runtime`, directly cited by `RuntimeBootstrapConfig::new`'s own documented `Overflow` behavior) and `EFFECT_PROVIDER_RESULT_FAILED` (`synapse-common`, used by the Runtime's own internal logic, not only by Providers, to interpret a failed Effect reply) — were omitted from `foundation.rs`'s re-exports without disclosure, discovered by independently cross-referencing every `pub` item in all six of `foundation.rs`'s dependency crates against its own re-export list, item by item.

**Resolution**, confined entirely to `sdk/src/foundation.rs`: both constants added to their respective re-export blocks, each with a justification comment matching the module's own established style. An Independent Engineering Re-Review independently re-derived both underlying claims directly from `runtime/src/lib.rs` and `common/src/lib.rs` (not accepted from the Amendment Report), confirmed both accurate, confirmed no additional public API or Runtime exposure was introduced, and confirmed the full workspace test suite (994 tests) passed unchanged, concluding `READY FOR FOUNDER IMPLEMENTATION APPROVAL`.
