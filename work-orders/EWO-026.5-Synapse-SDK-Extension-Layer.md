## 1. Purpose

`EWO-026.4` completed the Curated Entry Layer. This work order populates the Extension Layer — `ARCH-014` §5, item 4 — with two curated composition pairs, each independently demonstrated by pre-existing, evidence-backed usage across the codebase: `provider_success_reply`/`provider_failure_reply` (Effect Provider reply construction) and `durable_state_encode_versioned`/`durable_state_decode_versioned` (`DurableStateContract` versioned-byte-prefix wrapping, `ARCH-012` §5).

---

## 2. Architectural Authority

Every function traces to `ARCH-014` §5 item 4's own generalization test: a capability the Extension Layer makes reachable must already be expressible in terms of an existing Runtime or Durable-State Contract mechanism. The Provider-reply pair generalizes a pattern independently duplicated across all six reference Effect Providers (`http`, `filesystem`, `process`, `sqlite`, `timer`, `communication`). The versioned-encoding pair generalizes the domain-independent version-wrapping mechanism `ARCH-012` §5 recommends as its own default, independently duplicated across three pre-existing implementations (`services/persistence/src/internal.rs`, `runtime/src/lib.rs`, `runtime/tests/durable_actor_recovery.rs`), deliberately scoped to exclude the domain-specific payload conversion each implementation performs around it.

---

## 3. Objectives

1. Implement `provider_success_reply`/`provider_failure_reply`, generalizing the reply-construction pattern independently duplicated across all six reference Effect Providers.
2. Implement `durable_state_encode_versioned`/`durable_state_decode_versioned`, generalizing only the version-wrapping mechanism common to all three pre-existing `DurableStateContract` implementations, excluding domain-specific payload conversion.
3. Correct the module's own original claim of "exactly one" pre-existing `DurableStateContract` implementation to accurately state three, each individually named.
4. Prove, via integration test, that a `DurableStateContract` built entirely from Extension-layer functions genuinely round-trips through a real Runtime checkpoint/restore cycle.

---

## 4. Non-Goals

This work order MUST NOT, and its implementation does not:

- introduce any capability not already independently demonstrated by existing repository usage;
- generalize the domain-specific payload-conversion logic any of the three `DurableStateContract` implementations perform around their own version-wrapping;
- modify `foundation.rs`, `ergonomics.rs`, `prelude.rs`, or any Runtime, Persistence, Recovery, Scheduling, or Capability behavior;
- populate any Audit Pipeline or DX-series reference-application concern (tracked separately under `EWO-027` and `DX-001`, neither included in this work order's own scope or commit).

## 7. Engineering Amendment Record — Finding F01

An Independent Engineering Review of the original implementation found one Major finding: the module's own doc comment claimed "exactly one" pre-existing `DurableStateContract` implementation existed in the codebase, cited as the sole justification for the Provider-reply-only scope of this layer. A fresh audit, performed per this Amendment's own explicit instruction to follow the evidence rather than preserve the previous conclusion, found this claim false — three genuine, independent implementations exist (`services/persistence/src/internal.rs`, `runtime/src/lib.rs`, `runtime/tests/durable_actor_recovery.rs`), all `EWO-025`-era.

**Resolution** (Amendment v0.2.0): the false "exactly one" claim corrected to name all three implementations; the version-wrapping mechanism common to all three — and only that mechanism, deliberately excluding each implementation's own domain-specific payload conversion — generalized into `durable_state_encode_versioned`/`durable_state_decode_versioned`, added to `sdk/src/extension.rs` with five new tests in `sdk/tests/extension.rs`. An Independent Engineering Re-Review independently re-derived the three-implementation count directly from the repository (not accepted from the Amendment Report), independently re-verified the new functions' scope excludes domain-specific conversion, confirmed zero regression, and concluded `READY FOR FOUNDER IMPLEMENTATION APPROVAL`.
