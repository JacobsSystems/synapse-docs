## Executive Summary

This document completes the one deferral `ARCH-007` has named, by name, in four separate sections (§4, §12, §22, §24) since its own authoring: a real storage technology behind the `Persistence Service` contract. It does not redesign `ARCH-007`'s own Persistent Actor model — identity, ownership, restore ordering, deletion/retention, failure classification, audit obligations, and `ARCH-007`'s own fourteen original invariants all remain exactly as `ARCH-007` v0.5.1 states them, independently re-confirmed unchanged throughout this document; `ARCH-007` v0.5.0/v0.5.1's own later Durable-State Contract addition (§13.1–13.9) and its seven further invariants (15–21) are addressed directly in §5 below and found to sit one layer above this document's own scope. What it adds is the layer beneath: how a checkpoint is atomically written, how a corrupted or partial write is detected and never mistaken for valid data, how a stored representation's own format version is tracked so a future Runtime build can tell old data from new, and what class of storage technology satisfies `ARCH-007` §22's own existing prohibition on infrastructure lock-in.

Three findings are worth stating before the detailed sections below. First, this document is a genuinely new, standalone architecture, not a candidate for folding into `ARCH-007` — §5 does the identical consistency-review exercise `ARCH-009` §3 once did for itself, and reaches the opposite conclusion, for reasons stated there. Second, no storage backend is selected — a *class* of backend (embeddable, ACID, infrastructure-independent) is required, two named candidates within that class are identified as best-evidenced, and explicit selection criteria are given for the eventual Engineering Work Order to apply, exactly as this task's own instruction permits when premature optimization for one engine is not evidenced. Third, the capability-revalidation gap `IPR-003` found in the older, in-memory `Runtime::restore_actor_instance` path is explicitly assessed (§16) and found to be **outside this document's own scope** — a narrow `ARCH-002` §9 clarification, not a Durable Storage Mechanics concern, and not silently absorbed here.

## 2. Purpose

This document defines the architecture governing **durable storage mechanics**: how the durable representation of a Persistent Actor's own domain state (`ARCH-007` §7–§9) is physically written, atomically published, integrity-protected, versioned, and recovered, beneath the already-established `Persistence Service` contract (`ARCH-007` §12). It completes the transition `IPR-003` found this project ready to make: from a substantively complete, already-partially-implemented Persistent Actor *model* sitting atop a disclosed, honest, in-memory storage *stub*, to a model sitting atop genuine, crash-consistent durability.

This document codifies, and introduces no design beyond, `IPR-003` (Runtime Durability Requirements and Architectural Readiness Review), which concluded `READY FOR ARCH-011` after finding no remaining blocker, and `DES-001`/`ARCH-007`, whose own Persistent Actor model this document extends without amendment. Every architectural decision below traces to a specific `IPR-003` finding, a specific `ARCH-007` citation, or a specific piece of evidence `IPR-003` §4 already gathered; none is newly invented here.

## 3. Scope

**In scope:** the storage-backend abstraction boundary beneath `Persistence Service`; checkpoint-write atomicity and crash-consistency guarantees; the stored-representation envelope (version metadata, integrity metadata) and its ownership split from the actor-supplied payload; startup discovery of existing stored representations; storage-layer integrity verification and corruption detection; version-envelope-based backward compatibility; backend-evaluation criteria and two named, best-evidenced candidate classes; the storage-layer-specific consequences for Runtime integration with Actor lifecycle, Capability Authority, and Audit; and an explicit assessment of whether the `IPR-003`-identified in-memory restoration gap belongs to this document.

**Out of scope:** any redesign of `ARCH-007`'s own Persistent Actor model (identity, ownership, restore ordering, deletion/retention policy ownership, failure classification, audit obligations, the fourteen existing invariants — all reused, unmodified); Effect Coordinator state, Capability registrations, Timer, Scheduler, or Supervisor state durability, each already, independently excluded from persistence by existing, unmodified architecture (`ARCH-008` §22, `ARCH-007` §9) and consolidated once, for reference, in `IPR-003` §7 — this document does not restate that table, only relies on it; Audit-event durability, explicitly assessed and placed out of scope in §15; event sourcing, command replay, or durable-execution models — named, once again, as compatible future extensions, never designed here, on the identical basis `DES-001` and `ARCH-007` §24 already establish; distributed, cross-process, or clustered persistence (`ARCH-007` §3/§24, unchanged); any concrete Rust type, trait signature, or storage-format byte layout; any numeric performance target (`IPR-003` §11 already, correctly, left these as architectural questions this document resolves only where evidence supports doing so, per §10 below).

## 4. Non-Goals

Restated in full, consistent with §3: this document does not select a final storage backend (§14); does not design a general schema-migration mechanism (`ARCH-007` §13's own actor-owned-schema-evolution stance is unchanged); does not design distributed or clustered persistence of any kind; does not design encryption-at-rest as a mandatory requirement (§17); does not redesign `ARCH-002` §9's in-memory restoration mechanism (§16); does not design a Runtime Control API or Control Centre integration (§18 notes compatibility only, on the identical basis `ARCH-008` §29 already does for other future capabilities); does not fix a checksum algorithm, a compaction/vacuum policy, or a backup procedure.

## 7. Architectural Principles

- **Meaning and mechanics remain separated**, extended one layer deeper. `ARCH-007` §10 already separates what an actor's domain state *means* (actor-owned) from how it is *encoded and stored* (Persistence-Service-owned). This document separates encoding/storage mechanics further, into the actor-opaque payload and the Persistence-Service-owned envelope (§9) — the identical discipline, one layer down, never a new principle.
- **Truthfulness over convenience**, extending `ADR-0015`'s precedent through `ARCH-007` §18 into the storage layer specifically: a checkpoint that did not genuinely, atomically complete MUST NOT be observable as though it had (§10).

- **Explicit, never ambient, action on stored state**, extending `ARCH-008` §22's own established precedent for Effects ("actors, not the Runtime, are responsible for deciding whether to request an Effect again after restoration... never something the Effect Coordinator or Persistence Service does on the actor's behalf") to the specific open question `IPR-003` Q2 names — resolved in §11 by direct application of this exact, already-approved precedent, not a new principle invented for this document.
- **No redesign of existing architecture.** Every mechanism this document reuses — the `Persistence Service` contract, the restore sequence, the capability-revalidation requirement, the audit obligations — is reused unmodified; this document adds exactly one new architectural layer (the storage-backend abstraction, §9) beneath an existing, unmodified contract.

## 9. Storage Architecture

**Backend abstraction.** `Persistence Service`'s own internal implementation delegates to a swappable storage-backend abstraction, substitutable at Runtime composition time — architecturally identical in kind to how Scheduler, Supervisor, and Temporal Runtime are already substitutable (`ARCH-002` §6), and explicitly **not** the Effect Provider pattern (`ARCH-008` §11): a storage backend is reached only through `Persistence Service`, itself reached only through Runtime (`ADR-0016` Rule 2), never through the capability-authorized Effect-dispatch pipeline. Conflating the two would introduce a second, parallel extension mechanism this document does not create.

**Why a nested boundary, distinct from `ARCH-007` §22's own existing `Persistence Service`-level replaceability, is architecturally justified — added on independent review (`IAR-011` Finding 4), not present in this document's own original v0.1.0 text.** `ARCH-007` §22 already makes the whole of `Persistence Service` substitutable; it would be sufficient, in principle, for a future embedder simply to write an entirely new `Persistence Service` implementation per storage technology. The narrower, nested boundary this section introduces instead is justified by **responsibility**, **ownership**, and the concrete **architectural benefit** that follows from separating them:

- **Responsibility.** The storage-backend abstraction owns exactly, and only, raw byte-level durability for one opaque blob at a time: write, read, and existence-check, against whatever storage technology it wraps. It owns nothing about envelopes, checksums, or version semantics.
- **Ownership.** `Persistence Service` itself — not the backend — continues to own envelope construction, integrity-checksum computation and verification, and outer-version acceptability (§8's own ownership table, unchanged by this addition). The backend is never asked to understand what an envelope is; it stores and returns bytes.
- **Architectural benefit.** Because envelope/integrity logic sits in `Persistence Service` itself, above the backend boundary, every future backend substitution — SQLite today, a different embeddable store tomorrow — automatically inherits identical atomicity (§10), integrity (§13), and versioning (§12) guarantees without reimplementing any of them. Without this nested boundary, each full `Persistence Service` replacement would need to reimplement envelope and integrity handling independently, with no architectural guarantee that two different implementations enforce the guarantees in §10/§13 identically.
- **Interaction with `Persistence Service`.** The backend is invoked exclusively by `Persistence Service`'s own internal logic, never directly by Runtime, an actor, or any other component — it is not itself independently reachable, and `ADR-0016` Rule 2's reachability constraint applies to it exactly as it applies to `Persistence Service` as a whole.

This is additive precision, not a new design: the nested boundary was already implicit in §9's own original envelope/payload split (`Persistence Service` must sit *above* whatever stores raw bytes for the envelope/payload separation to mean anything); this correction only makes the resulting ownership split explicit.

**Envelope/payload separation.** Every stored representation consists of two, structurally distinct parts:

- the **payload** — the actor-supplied structured domain-state representation, opaque to `Persistence Service`'s own logic beyond encode/decode (`ARCH-007` §9, §13, unchanged);
- the **envelope** — Persistence-Service-owned metadata: an outer format-version identifier; a **Durable-State Kind Identifier** (added on this document's own Independent Architecture Re-Review, resolving Finding F-3 — `ARCH-007` §13.5 already required this field to exist here; this document had not yet defined it) — the stable, actor-definition-assigned identifier `ARCH-007` §13.5 defines, distinguishing which Durable-State Contract a stored representation was encoded by, so that `Persistence Service` can compare it against the Runtime-supplied contract's own identifier at restore time (`ARCH-007` §13.5, §13.8); an integrity checksum; and the checksum algorithm's own identifier, so the algorithm itself may evolve without invalidating already-stored data. The Durable-State Kind Identifier's own comparison logic, and the failure semantics of a mismatch, are `ARCH-007`'s own to define (§13.5, §13.8) — this document's own contribution is limited to defining that the envelope carries this field at all, the identical mechanics-only boundary every other envelope field in this list already observes.

This resolves `IPR-003` §14 Q4 (version-envelope ownership) directly: the **outer** envelope version is Persistence-Service-owned (a mechanics concern — "what encoding scheme was this written with"); the **inner**, domain-meaningful schema version remains actor-owned (`ARCH-007` §13, unchanged — "is this representation still acceptable to my own current logic"). Neither party's version tag is the other's concern, the identical meaning/mechanics separation §7 already states as this document's own governing principle.

**Snapshot strategy.** A checkpoint is a whole-state overwrite of the current stored representation, matching `DES-001`'s own recommended first-milestone design and `ARCH-007` §16's own "Checkpoint (persist): durable state is created or updated" language. No incremental-diff or append-only journal mechanism is introduced. This is explicitly **compatible with**, and does not preclude, a future event-sourced or journal-based backend implementation — `DES-001`'s own named future extension — since the backend-abstraction boundary this section establishes does not itself assume whole-snapshot semantics; it is a property of the first-milestone backend choice, not of the architecture.

**Backend independence.** No storage-backend implementation may be architected to require a specific replication, clustering, or hosted-service infrastructure as a precondition for conformance — restating `ARCH-007` §22's own explicit prohibition without exception, extended to this document's own backend-abstraction boundary directly.

## 10. Atomicity

Guarantees, not algorithms, per this document's own governing instruction:

- **Checkpoint atomicity.** A checkpoint operation is atomic from the perspective of any subsequent `retrieve`: either the complete new representation becomes visible, or the complete prior representation (if any) remains visible. No intermediate, partial state is ever externally observable.
- **Interrupted writes.** An interruption at any point during a checkpoint's own write — power failure, process crash, kernel panic, or any other unexpected termination `IPR-003` §8 already names — MUST leave the storage layer in a state where the next `retrieve` returns either the complete prior representation or the complete new one, never a mixture. This is the direct, storage-layer-specific extension of `ARCH-007` §18's already-established "no partial write may be treated as authoritative" rule.
- **Partial persistence.** A checkpoint is a single atomic unit from `Persistence Service`'s own external contract regardless of the actor-supplied payload's own internal size or structure.
- **Crash consistency.** Every interruption point MUST leave the storage layer able to answer a subsequent `retrieve` with one of exactly three truthful outcomes: a complete, valid representation; a truthfully-absent representation (`ARCH-007` §18's "missing" case); or a truthfully-detected corrupted representation (§13, below) — never silent, undetectable corruption, and never a fourth, ambiguous outcome.
- **Deletion consistency.** A deletion operation is itself atomic: either the stored representation is fully removed, or it remains fully intact. This extends, without altering, `ARCH-007` §17's own already-established deletion-coordination ordering (validate authority → cancel timers → audit → attempt deletion → audit outcome) with the storage-layer-specific guarantee that the "attempt durable-state deletion" step itself cannot leave a partially-erased representation.
- **Metadata consistency.** The envelope (§9) and the payload it describes MUST be updated atomically together — a state where the payload is new but its checksum still describes the prior payload, or vice versa, is prohibited, since it would defeat §13's own corruption-detection guarantee.
- **Ordering, restated as a single rule:** a new representation is never permitted to overwrite or displace the prior one until the new one is confirmed atomically durable — "write-then-publish," never "delete-then-write" — the direct precondition for every guarantee above.

## 11. Recovery Architecture

**Startup discovery**, a `Persistence Service`-internal mechanical concern distinct from Runtime-level restoration *policy* (below): `Persistence Service` MUST be able to enumerate the set of `ActorId`s for which a stored representation currently exists, on demand. This is a mechanics-only capability — it decides nothing about whether, or when, any of those representations should be used to reconstruct a live instance.

**Runtime-startup restoration policy — `IPR-003` §14 Q2, resolved.** Restoration is always explicit and on-demand, never automatic as a side effect of Runtime startup. This is not a new principle: it is the direct, evidence-grounded application of `ARCH-008` §22's already-approved precedent for the structurally identical question in the Effect domain. `ARCH-008` §22 states this across two adjacent bullets, quoted here separately and in the order they actually appear, corrected from this document's own original v0.1.0 text, which presented a spliced, ellipsis-joined composite of the two as a single continuous quotation (`IAR-011` Finding 3): first, that persisted domain-level intent "is the actor's own affair to encode, never something the Effect Coordinator or Persistence Service does on the actor's behalf"; and, as the very next bullet, that "actors, not the Runtime, are responsible for deciding whether to request an Effect again after restoration." Read together, in their own original order, both already establish the identical principle this section applies to durable-restore-at-startup: explicit, actor-owned decision-making, never an ambient Runtime default. This is also consistent with `ARCH-007` §17's own existing "explicit, never ambient" discipline for deletion. No implementation of this architecture may cause a Runtime boot sequence to automatically reconstruct a live instance from a discovered stored representation without an explicit instruction to do so.

**Checkpoint identification.** Because §9 establishes whole-state overwrite as the first-milestone snapshot strategy, there is at most one current stored representation per `ActorId` at any time — "identification" reduces to existence (does a representation currently exist for this `ActorId`) plus its own envelope. A future event-sourced backend, should one be built, would need its own, separate identification scheme; this document does not design one, consistent with §9's own explicit deferral.

**Recovery ordering.** Unchanged from `ARCH-007` §15's own seven-step sequence. This document's own contribution is ensuring `retrieve` (step one of that sequence) satisfies §10's atomicity guarantees, never a redesign of the sequence itself.

**Validation sequence**, extending `ARCH-007` §15/§18 with the storage-layer-specific ordering those sections did not need to state: integrity verification (§13) precedes decode; envelope-version acceptability (§9) is checked next; decode follows; the actor's own `import_domain_state` (`ARCH-007` §13) performs the final, actor-owned acceptability check. Checking integrity first prevents attempting to decode bytes already known to be corrupted.

**Corruption handling.** Unchanged from `ARCH-007` §18: a corrupted stored representation is treated identically to a failed restore, and is architecturally distinguishable, in the audit record, from a missing one — restated here as the storage layer's own obligation to make that distinction detectable at all (§13).

**Incomplete checkpoint handling.** By construction of §10's own atomicity guarantee, an incomplete checkpoint is never externally observable as a stored representation at all — it is a storage-internal transient state, never a case the recovery sequence must separately handle. This is the guarantee that makes a dedicated "incomplete checkpoint" recovery case unnecessary at the architecture level.

**Recovery failure behaviour.** Unchanged from `ARCH-007` §18: a failed restoration fails cleanly, the logical actor is left with no live instance, and no ambient retry or silent fallback to default state occurs.

## 12. Versioning and Migration

- **Schema evolution** of an actor's own domain-state representation remains entirely actor-owned, unchanged from `ARCH-007` §13. This document does not introduce, and does not preclude, a general migration mechanism.
- **Runtime upgrades.** The outer envelope version (§9) is what allows a future `Persistence Service` build to detect that a stored representation was written by an older encoding scheme, and either decode it (if still supported) or fail cleanly and truthfully (if not) — never silently misinterpret incompatible bytes as valid.
- **Backward compatibility.** `Persistence Service` SHOULD support decoding at least the immediately prior outer-envelope version where practical. This is a SHOULD, not a MUST — no specific compatibility window is fixed at the architecture level, consistent with `ARCH-002` §22's own established pattern of deferring numeric/version-window policy to implementation. What is fixed, without exception: an unsupported envelope version is always a truthful, distinct failure, never a silent misinterpretation.
- **Version metadata**, restated from §9 for completeness: encoding-scheme identifier and version; Durable-State Kind Identifier (`ARCH-007` §13.5); integrity-checksum value; checksum-algorithm identifier.
- **Migration strategy** — a general, automated migration mechanism between envelope or schema versions is explicitly not designed here, consistent with `ARCH-007` §13's own identical stance for actor-owned schema evolution.

## 13. Storage Integrity

- **Integrity verification.** A checksum is computed over the encoded payload at write time, stored in the envelope (§9), and re-verified at read time before decode is attempted.
- **Corruption detection.** A checksum mismatch is a corrupted-representation outcome, architecturally distinct from a missing one (`ARCH-007` §18, unchanged) and never silently accepted as valid.
- **Checksum strategy.** This document fixes that a checksum MUST exist and MUST be verified before decode; it does not fix the algorithm. A fast, non-cryptographic checksum (e.g., a CRC family) reliably detects accidental corruption (torn writes, bit rot, truncation) at low cost; a cryptographic hash additionally provides tamper-evidence against deliberate modification, at higher computational cost. This trade-off is named, not resolved, here — an implementation-phase choice, consistent with `ARCH-002` §22's numeric/algorithm-policy deferral pattern, and revisited in §17's own security discussion.
- **Metadata validation.** The envelope itself (§9) MUST be structured so that its own corruption is independently detectable — a corrupted envelope must never be capable of producing a false "valid" read. This document does not fix the envelope's own concrete format, only this requirement of it.
- **Recovery safeguards.** Restated from §10's own ordering rule: a prior stored representation is never removed or overwritten until the new one is confirmed atomically durable.

## 14. Backend Evaluation

**No backend is selected by this document.** Consistent with this task's own explicit instruction, and with `ARCH-002` §22/`ARCH-007` §22's own established pattern of treating storage technology as a permitted variation, this section states the *class* of backend §9's own independence requirement demands, names the best-evidenced candidates within that class, and gives explicit selection criteria for the eventual Engineering Work Order.

## 16. Restore Semantics Assessment

**The finding.** `IPR-003` §11 (Risk R1) independently confirmed, by direct call-path tracing, that `Runtime::restore_actor_instance` — the *older*, in-memory Suspended→Resume mechanism `ARCH-002` §9 governs, architecturally distinct from `ARCH-007`'s own durable-restore path — performs no capability revalidation anywhere in its call path. `core/lifecycle-guardian`'s own source comments disclose this honestly: the crate has no path to Capability Authority (`ADR-0016`) and does not claim to perform revalidation it cannot honestly perform.

**Whether this belongs to ARCH-011.** No. This document's own scope (§3) is durable storage mechanics beneath `ARCH-007`'s already-correct model. `Runtime::restore_actor_instance` is not part of that model at all — it predates `ARCH-007`, is governed exclusively by `ARCH-002` §9, and its own gap exists independently of whether durable storage is ever built. Absorbing this fix into `ARCH-011` would silently redesign `ARCH-002` §9 under cover of a Durable Storage Mechanics architecture, exactly the kind of scope drift this task's own instruction prohibits ("do not silently alter unrelated Runtime architecture").

**Whether architectural amendment is required.** A narrow one, to `ARCH-002` §9 itself — not a redesign. `ARCH-007` §10 already, successfully, resolved the structurally identical problem for the *durable* restore case: rather than expecting Lifecycle Guardian (which has no path to Capability Authority) to trigger revalidation, Runtime triggers it directly, and Capability Authority alone performs it, in both cases. The same resolution, applied to `ARCH-002` §9's own original in-memory case, would close this gap without inventing anything new — a direct, evidence-grounded application of a pattern this corpus has already, once, proven correct.

**Whether an ADR is required.** Yes — a short, targeted ADR (or a narrow `ARCH-002` amendment following the identical "targeted correction pass" shape `ARCH-007`'s own v0.1.0→v0.2.0 revision already used) is the right instrument, scoped to exactly this question and citing `ARCH-007` §10 as its own direct precedent. This document recommends that ADR be authored as a separate, future, narrowly-scoped item. It is not authored here, and this document performs no part of it.

## 17. Security

- **Integrity.** Checksums (§13) reliably detect accidental corruption. They do not, on their own, provide cryptographic tamper-evidence against a deliberate adversary capable of recomputing a matching checksum — a distinction this document states honestly rather than implying a stronger guarantee than a fast, non-cryptographic checksum actually provides. Where stronger tamper-evidence is wanted, a cryptographic hash is the implementation-phase choice already named as available in §13.
- **Authorization boundaries.** Unchanged from `ARCH-007` §20: every protected persistence operation remains capability-authorized through the existing, unmodified Capability Authority model; no second, parallel, or informal authorization system is introduced by this document; `Persistence Service` continues to grant no authority and define no security policy of its own, extended without exception to the storage-backend abstraction §9 introduces beneath it.
- **Capability interaction.** No new capability or operation string is introduced. The existing `"persistence.checkpoint"`/`"persistence.restore"`/`"persistence.delete"` operation strings, already independently confirmed correctly implemented (`IPR-003` §3), remain the complete set this document's own storage layer sits beneath.
- **Confidentiality.** Not required by this architecture. No governing document in this corpus (`GOV-002`, `GOV-015`, `ARCH-001`, `ARCH-007`) currently states a confidentiality requirement for actor domain state at rest, and adopting encryption-at-rest without an evidenced requirement would violate `GOV-002` §6.1/`GOV-004`'s own "correctness before convenience," here read as "capability before convenience" — do not add complexity unsupported by evidence. Should a future, evidenced confidentiality requirement emerge, it is architecturally addable as a backend-specific capability (an encrypting backend implementation) without requiring redesign, since backend substitution is already a first-class extension point (§9). This document names the possibility; it does not require it.
- **Auditability.** Unchanged — see §15's own Audit row.

## 18. Operational Architecture

- **Diagnostics.** Corrected on independent review (`IAR-011` Finding 5): this document's own original v0.1.0 text claimed a future "inspect stored metadata without full decode" capability was "architecturally straightforward" without distinguishing what such inspection can and cannot actually see. Four, architecturally distinct kinds of validity exist for any one stored representation, and a diagnostic capability can only ever address the first two without a full decode:
  - **Envelope integrity** — whether the envelope itself (§9's own outer version tag and checksum fields) is structurally well-formed and internally uncorrupted (§13's own "metadata validation" requirement). Inspectable without decoding the payload.
  - **Payload integrity** — whether the payload's own stored bytes match the checksum the envelope records (§13). Inspectable without decoding the payload — the checksum is computed and verified against the encoded bytes directly, never against their decoded meaning.
  - **Payload compatibility** — whether the payload's own outer encoding-scheme version (§9, §12) is one the current `Persistence Service` build still knows how to decode at all. Inspectable without a full decode of the *contents*, but requires reading the envelope's own version field, which the two rows above already cover.
  - **Payload semantic validity** — whether a successfully decoded payload remains acceptable to the actor's own current domain logic (its own inner schema version, `ARCH-007` §13). This is **not** inspectable without a full decode and a call into the actor's own reconstruction logic — it is the one category, of the four, a metadata-only diagnostic capability cannot address, because the actor's own inner version is opaque to `Persistence Service` by the same design that makes the envelope/payload separation (§9) meaningful in the first place.

  A future diagnostic capability may therefore truthfully report envelope integrity, payload integrity, and payload compatibility without a full decode; it cannot truthfully report payload semantic validity without one. Any future implementation MUST NOT represent a metadata-only check as having confirmed semantic validity — doing so would misstate what was actually verified, the identical truthfulness discipline `ARCH-007` §18/§19 already require generally. `ARCH-007` §14 continues to name "inspection of persistence metadata where applicable" only as a conceptually anticipated future protected operation, not designed by either document.
- **Maintenance** (compaction, vacuum, or equivalent backend housekeeping) is entirely backend-specific and is correctly left to implementation, consistent with §14's own refusal to select a backend.
- **Backup compatibility.** An embeddable, single-file-class backend (§14) offers a straightforward file-level backup story as a direct consequence of the required backend class, not as a separate architectural commitment this document makes.
- **Future tooling / Control Centre integration.** See §15's own Runtime APIs row — compatible, not designed, on the identical basis `ARCH-008` §29 already establishes for naming future compatibility without building it.

## 20. Architectural Invariants

**Numbered independently, beginning at 1, as this document's own first invariant set — distinct from, and additive to, `ARCH-007`'s own fourteen invariants, which remain entirely unmodified and unrenumbered by this document.** This follows `ARCH-010` §22's own established convention exactly (itself a standalone document extending an existing architecture's ownership model), corrected here from this document's own original v0.1.0 text, which continued `ARCH-007`'s numbering directly and was found, on independent review (`IAR-011` Finding 1), to contradict the very precedent it cited itself. A citation to "`ARCH-011` invariant 3," for example, is unambiguous by this numbering; a citation to "invariant 20" alone, under the prior scheme, was not.

Any implementation of this architecture MUST preserve the following, in addition to and without altering any of `ARCH-007`'s own fourteen invariants:

1. A checkpoint-write operation is atomic: no partial or torn write is ever externally observable via `retrieve` (§10).
2. A stored representation's envelope and payload are updated atomically together; neither may describe the other incorrectly (§10).
3. A new stored representation is never permitted to displace the prior one before the new one is confirmed atomically durable (§10).
4. Integrity verification occurs before decode is attempted on any retrieved representation (§11, §13).
5. A corrupted stored representation is never silently accepted as valid, and remains architecturally distinguishable from a missing one (§13, unchanged from `ARCH-007` §18, restated here as a storage-layer obligation).
6. An unsupported outer envelope version is always a truthful, distinct failure, never a silent misinterpretation (§12).
7. No storage-backend implementation may require a specific replication, clustering, or hosted-service infrastructure as a precondition for conformance (§9, extending `ARCH-007` §22 without exception).
8. Restoration is never automatically triggered as a side effect of Runtime startup; it is always an explicit, on-demand act (§11).
9. This document introduces no new Trusted Core component and alters no existing Trusted Core component's own `ARCH-002` §6 responsibility.

## 22. Conformance Requirements

A conformant implementation of this architecture:

- **MUST** satisfy every atomicity guarantee in §10 for every checkpoint, restore, and delete operation.
- **MUST** verify integrity before attempting to decode any retrieved representation, and MUST distinguish a corrupted representation from a missing one in both its return value and its audit record.
- **MUST** be able to enumerate the set of `ActorId`s for which a stored representation currently exists, on demand (§11).
- **MUST NOT** require a specific replication, clustering, or hosted-service infrastructure as a precondition for conformance.
- **MUST NOT** automatically trigger restoration as a side effect of Runtime startup.
- **MUST NOT** introduce a second, parallel, or informal authorization mechanism for any protected persistence operation.
- **MUST NOT** introduce a new `AuditEvent` field; new `event_type` string values only, where genuinely needed, consistent with `ARCH-008` §17.1's own established discipline.
- **SHOULD** support decoding at least the immediately prior outer-envelope version where practical.
- Required engineering evidence for the eventual implementing Engineering Work Order, at minimum: a passing test suite exercising every failure and atomicity case named in §10–§11; the backend-selection criteria in §14 applied and disclosed, not silently assumed; formatting, lint, build, and test validation all clean; a truthful Engineering Report (STD-001 §47) disclosing what was implemented, what was deferred, and any known limitation — the identical evidentiary bar `ARCH-007` §25 and `ARCH-008` §11.4 already establish for their own conformant implementations.
